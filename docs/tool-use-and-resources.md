# 工具接入与共享资源设计

[项目 Roadmap](../README.md#roadmap) · [文档索引](README.md)

**基础 Tool Use 负责操作工具并采集证据，共享资源调度负责多个 Issue 如何分配和复用工具背后的环境。** 例如操作页面并截图属于 Tool Use；浏览器实例分配、占用排队与故障回收属于共享资源调度。

场景所需的 Browser、Computer Use 或 Simulator 控制能力随工具接入提供，是对应 Evidence / Verify 的前置。首次接入即具备环境身份、授权、必要隔离、占用保护与清理，后续再统一资源抽象与调度。Worker Pool 管理执行容量，共享资源调度管理具体环境的占用。

工具接入依赖 Harness / Daemon、候选身份与权限；统一调度基于已接入工具的环境契约；跨 Host 验证进一步依赖稳定资源 Provider 与构建、证据身份链。完成状态统一维护在 README 的 Roadmap，已实现边界见[当前状态](current-status.md)；设计背景来自已归档的 [0908 Plan](archive/workspace-ai-product-plan-2026-09-08.md)。

下述契约是设计要求；具体 Provider、协议与库尚未定案。实施时复用原生 Harness 已有能力和实际结果，先验证所选工具的事件可见性，不为统一抽象重写一套通用 Harness。

## Basic Tool Use

**交付目标：** Agent 能操作场景所需工具并采集真实证据，供后续 Evidence / Verify 使用。先支持本地执行，工具范围覆盖 Shell、测试、HTTP，以及需要交互验证时的 Browser、Computer Use 和 Simulator 控制。

> 当前实现状态：已落地的部分是 Evidence 判定侧的确定性采集器——固定命令 checker、项目自带命令（`project_command`，退出码即判定）和受控本地 Node HTTP 目标（GET/HEAD、127.0.0.1、无外部网络），全部由 Foundry 在候选只读沙箱内执行并把 stdout/stderr/状态码/响应体封成 Material（见 [Evidence & Verify v1 §4](evidence-and-verify-v1.md#4-材料采集与独立初判)）。Issue 实现侧 Agent 通过原生 SDK/CLI 自带工具在 OS 沙箱约束的候选 Worktree 中工作，但那不是本节设计的 Foundry 自有 Tool Use 层：**一般 Shell/工具调用记录为证据、Browser、Computer Use、Simulator 均未实现**（代码里只有 Evidence 阶段会话对 browser_use/computer_use 等能力的禁用清单，没有浏览器或桌面自动化实现）。下列“接下来做/完成标准”仍属路线图设计，不据此宣称完成。

**接下来做：** 从 Shell、测试运行器和 HTTP 请求等基础工具开始，明确调用、输入、输出、退出状态与超时的记录方式；补齐 Chat 中的工具过程、结果与必要交互。Web 验证接入浏览器操作与截图，桌面或移动端验证按场景接入 Computer Use 或 Simulator 操作及材料采集，不要求一次支持所有类型。

首次接入交互工具就要具备对应环境的身份、授权、必要隔离、占用保护与清理，确保操作和材料属于正确 Issue。后续共享资源调度再将这些能力统一成可分配、可排队、可复用的管理层。

**完成标准：** 选定场景的操作与证据采集可实际执行；成功、失败和超时都保留结果，并能对应到正确 Issue、候选状态与环境。Agent 的文字总结与工具原始输出分开；工具所需权限明确，人工回应后可继续工作，结束后能清理对应环境。

依赖 Harness / Daemon、候选身份与基础权限；相应工具能力是对应场景 Evidence / Verify 的前置。无需先完成统一共享资源调度、通用插件系统或多机资源池。

### 最小接入与证据契约

工具接入与最小 Evidence 契约一起设计：从 Issue、完成条件与候选身份出发，保留实际调用、参数、来源、环境/构建、结果或错误及材料引用，再由 Verify 作出判断。不必等完整 Evidence 页面做好，但也不能先做只有展示、无法关联候选的工具记录。

先选一种可复现的真实工具链，例如本地测试或 HTTP 验证；若当前目标承诺 Web 交互验证，同一条链就需要浏览器操作和截图。Computer Use、Simulator 按具体交付场景接入，不因为 Roadmap 列出类型就一次完成所有适配。

浏览器控制发生在受控实例或上下文中，Web 展示预览与材料；不依赖父页面读取任意跨域 iframe。执行宿主机上的权限、隔离、凭据和外部副作用仍由明确边界约束；原生 Harness 能运行命令不代表 Foundry 已具备完整的授权交互与证据采集。

首个小改动至少验证一次成功和一次失败/超时的真实结果归属，后续扩展候选变化、历史回放与中断恢复。工具原始记录保持事实，Agent 的解释单独呈现。

## Shared Resource Scheduling

**交付目标：** 统一管理多个 Issue 对单机和多 Host 上的浏览器实例、桌面会话、Simulator、端口等共享资源的分配、独占、排队、释放与故障回收，支持异地验证。

实现先从单机做起，再扩展跨 Host；两者属于同一项 Roadmap 能力，异地验证是它的应用场景。单机分配与回收完成后，还需补齐跨机授权、构建传输、版本关联和断线恢复，才能实现可信的异地验证。

**接下来做：** 在已接入的 Browser 或 Simulator 环境上试点统一资源身份、容量与占用记录、分配队列、释放重置、健康检查和故障回收；再扩展到其他已接入资源。各工具的基础操作与证据采集由 Tool Use 提供，本项负责跨 Issue 的竞争与复用。

**单机完成标准：** 两个 Issue 争用同一资源时不会串台或接管对方环境；资源可回收，清理失败的实例不会继续被发放。单纯资源排队不进入等待人介入的 Blocked。整项能力的完成还需通过下方跨 Host 场景验证。

依赖已接入工具及其最小环境身份、占用、清理与权限契约；统一调度不阻塞基础工具操作和对应 Evidence / Verify。

资源身份包含所属 Host、实际实例与持有者。超时或租约过期不能直接证明旧 Agent 已停止操作；回收后重新分配前需要确认旧占用失效、环境健康且隔离成立。先做简单队列与明确独占，跨 Workspace 公平性、配额和复杂多资源协同按实际瓶颈扩展。

### Cross Host Verification

**交付目标：** Build here, verify there：在一台机器构建，在另一台具备所需环境的机器验证。

**接下来做：** 多 Daemon 资源登记、授权、构建或材料传输、环境身份与断线恢复。先选一个真实场景验证，不一次抽象所有设备。

**完成标准：** 证据可追溯到正确的候选、构建和验证环境，旧构建或错误环境不会被当作有效成功；断线不造成重复占用或未经授权的操作。

依赖稳定的资源 Provider 和证据身份链。
