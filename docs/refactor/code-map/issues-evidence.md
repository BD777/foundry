### Encapsulation observations

- **"Evidence" vs "issue" naming split cuts across one concept.** Contract/clarification/review/accept live in files named `evidence_*` (`S/httpapi/evidence_clarification.go`, `S/sqlitestore/evidence_clarification.go`, `evidence_issue_creation.go`), next to `issue_*` files for the same flow (`S/httpapi/issue_clarification.go`, `issue_contracts.go`). `store.EvidenceStore` (`S/store/evidence_store.go:16`) contains `CreateIssueIdempotent`, `RecordIssueStatusQuestion`, `AskClarification`; Issue lifecycle is spread over three more interfaces in `S/store/store.go` (`IssueExecutionStore` :134, issue CRUD :205-213, daemon claim/run :251-255).
- **Issue claim/run lives in the daemon registration file.** `S/sqlitestore/daemon.go` mixes `RegisterDaemon`/`SyncChats` with `ClaimIssueExecution`, `startIssueRun`, `appendRunEvent`, `completeIssue`. Issue persistence helpers `saveIssue`/`saveRun`/`saveArtifact` sit in the generic `S/sqlitestore/sqlitestore.go`.
- **Status transitions mostly, not only, via `IssueLoop`.** 8 `Apply` calls (`issue_contracts.go:252`, `evidence_clarification.go:260`, `evidence_acceptance.go:192`, `daemon.go:358,471,589`, `issues.go:192,224`), but `UpdateIssueStatus` `S/sqlitestore/issues.go:114` writes `issue.Status` directly. It and `ClaimNextIssue` (`daemon.go:234`), `ListRunEvents` (`issues.go:246`) are on production interfaces but called only from tests.
- **A Run is stored four times.** Each execution event lands in `agent_session_events`, `run_events` (`saveRunEvent`), `runs.payload_json.events`, and `issues.payload_json.run.events` (`S/sqlitestore/daemon.go:500-529`); the Run is a mirror of the session (`S/httpapi/issue_execution.go:12-15`). The worker also builds its own `Run`/`AcceptanceArtifact` (`W/issue-execution.ts:150-170`). `AcceptanceArtifact` (legacy) and `AcceptanceDecision` (evidence) are both called "acceptance".
- **Two notification paths for Issue changes, used inconsistently.** `s.issues.updated` (publishes + runs observers: Feishu, pending items, workspace digests) vs `projectionsChanged(..., fieldIssues)` (data invalidation only). HTTP request-changes (`issues_http.go:99`), contract confirm (`issue_contracts.go`), create and claim use only the latter; the Feishu equivalents (`feishu_issues.go:72,99`) and daemon paths use the former, so observers miss web-originated changes.
- **Reads that write.** `CurrentReview` (`S/sqlitestore/evidence_review.go:121-223`) inserts a `review` record and saves the Issue; `GET /api/issues/{id}/review` and `refreshIssueReview` (`S/httpapi/evidence_events.go:13`, which calls it purely for the side effect) depend on that.
- **Issue business logic inside the Feishu adapter.** `S/httpapi/feishu_issues.go` (227) implements create/route/confirm for `S/feishu/issues.go` instead of sharing a service with the REST handlers (see duplicates 8, 9, 10).
- **Generic keyed lock in an Issue file.** `lockIssueMutation` `S/httpapi/issue_environment.go:14` is a `sync.Map` of mutexes never removed, also keyed by `verification-dispatch/<id>`, `verification-issue/<id>`, `evidence-recovery/<ws>` (`evidence_routes.go:207-209`, `evidence_recovery.go:15`).
- **Workspace Git readiness rides on the Issue-environment message.** `S/httpapi/issue_git.go:63-70` sends `issue_environment` with `issueId:""` and actions `git_status`/`initialize_git`; the worker handles it in `W/issue-environment-rpc.ts:21-33`. Workspace concern, Issue-shaped channel.
- **`ExecutionStore` does not own its layout.** Paths are re-derived with `"../../acceptances"`/`"../../runs"` and per-feature roots (duplicate 17). `execution-types.ts` holds both registration (workspace) and acceptance (journal) types.
- **Worker `issues.ts` is a legacy bundle.** One 545-line module holds review sync, patch integration, artifact mirroring, legacy preview, and port helpers the live `issue-preview.ts` imports; it also re-exports `executeIssue` (:31), so live callers (`W/daemon/issue-run.ts:5`) import execution through the legacy module.
- **`evidence-rpc.ts` is a 994-line hub.** It holds action dispatch, upload sealing, candidate gating, HTTP target startup, dependency prep, file export, verify/judge/check orchestration and program judgment (`W/evidence-rpc.ts:72-992`). Accept is delegated out (`evidence-acceptance.ts`), the rest is not.
- **Evidence client sits in a feature.** `F/features/issue-detail/evidence-api.ts` (293) is the only REST client outside `F/api/`; `F/api/issues.ts` covers the non-evidence half of the same `/api/issues/{id}` surface.
- **Sandbox is a clean leaf with one leak.** `W/sandbox/index.ts` is the only entry for 10 callers, except `W/evidence-dependencies.ts:15`, which imports `protectedHostPaths` from `sandbox/host.js`. Sandbox capability is also mirrored server-side as capabilities and role checks (`S/store/devices.go:197-202`, `S/connectors/module.go:76`, `S/httpapi/mcp_verification.go:23`).
- **"Verification" names three things:** an AgentSession source (read-only verifier), a worker-internal `SessionRole` for the evidence judge (`W/session/types.ts:6`), and the evidence `Verification` record. `W/session/` exists mainly for the judge, while Issue/verifier/clarification sessions run through `runWorkspaceSession` in the same directory.
- **Candidates to extract as shared modules (from the duplicates above):** contract gate/human-actor predicate (Go + TS); one canonical-digest implementation per language tested against each other; an Issue message router used by web and Feishu; a "sandboxed read-only workspace session" builder (clarification/verifier); an execution-store path API (journals, runs, outboxes); one typed Go mirror of `EvidenceWorkerRequest`/environment payloads under the contract audit; and a shared constant for turn-event discriminators like the steer label.
