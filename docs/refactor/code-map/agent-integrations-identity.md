### Encapsulation observations

- **Personal agent is spread across about 30 httpapi files (8023 LOC, 17% of httpapi's 47k).** Its pure-rule package `personalagent` is 1534 LOC. Queue drain logic, prompts, MCP planners, Feishu desk adapters, the knowledge pipeline and run resolution all sit on `*Server` with private mutexes in server.go. The workspacedigest package shows the alternative already in use: a package with a `Sources` interface, glued by httpapi (workspacedigest/doc.go).
- **Knowledge is filed as personal agent but is its own subsystem.** It has its own REST tree, four durable queues, a daemon message, worker file I/O and the `read_knowledge` MCP tool, yet it lives in `personal_agent_knowledge*`/`_migrations`/`_publications`/`_replica_cleanup`. On the worker, its handler (and context patches) sits inside the generic daemon/handlers/files.ts rather than its own handler module.
- **Durable job queues are rebuilt per feature:** inbox, operations, maintenance, context patches, knowledge mutations/migrations/replica forgets, and reminders/digest claims. Each has its own table, Due/Claim/Retry methods, optional store interface, ticker loop and TryLock mutex (see items 10 and 11). The same shape is a candidate for a shared queue module; session inbox and chat queue (other groups) have it too.
- **The `store.Store` mega-interface sits alongside about 14 optional interfaces reached by runtime type assertion.** As a result, a missing implementation surfaces as a 501 at request time, not at compile time (item 11).
- **"Connectors" is one module in name but three in code.** `connectors.Module` wraps `externalaccounts.Service` (3818 LOC, mostly Feishu/Cloudflare OAuth) plus device-held state. The device-held business logic (refresh coalescing, authorization flows, workspace bindings, execution devices) is in httpapi/connectors.go (921 LOC), not in `connectors.DeviceHeld`. Cloudflare's provider is in externalaccounts/cloudflare.go, its gateway in connectors/cloudflare_gateway.go, its writes in connectors/cloudflare_writes.go, and its HTTP in three httpapi files.
- **Three near-homonyms for distinct concepts:** "external accounts" (server-held OAuth logins), "external connections" (device-registered model gateways, really a profile `connectionType`, §6), and "connectors"/"device connectors" (device-held CLIs). Web folds external accounts and device-held connectors into `features/external-accounts` (6162 LOC), while external connections live under `features/devices`.
- **The Cloudflare gateway reuses Feishu tables:** `CreateFeishuGatewayGrant` with placeholder hashes (cloudflare_gateway.go:94) and `store.FeishuGatewayGrant`. This leaks the "Feishu gateway" name into a provider-agnostic handle grant. `externalaccounts.HandleIssuer` is already generic, so a provider-neutral grant store is the natural seam.
- **Feishu is split over five server places:** `feishu` (bots/cards/DM desk/Issue thread), `feishuevents` (connection hub), `feishugateway` (CLI proxy), `externalaccounts/feishu*.go` (OAuth/tenant token/scopes), and httpapi (feishu.go, feishu_issues.go, feishu_events.go, personal_agent_feishu.go, external_accounts_gateway.go). There are two Feishu HTTP clients, the lark SDK and the hand-rolled one (item 15). `feishu.WSManager` is named for a socket but holds none; it routes bot messages, and feishuevents owns the socket. The Feishu Issue flow is split between feishu/issues.go and httpapi/feishu_issues.go (httpapi implements host callbacks).
- **The access model is spread over four abstractions in httpapi:** `accessScope` (access.go), `visibility` (visibility.go), `paScope` (access.go:270), and route `accessRule`s (routes.go), plus `agentRouteAllowed` (policy.go). There are also ad-hoc guards (`personActor`, `currentAccount`, `requireExternalAccountOwner`, `requireConnectionOwner`) with differing actor acceptance (item 13). Only signedIn/personOnly/adminOnly are distinct rules; `inHandler()` is used for many connector/profile routes, so their checks are invisible in the route table.
- **Token issuance and hashing layers are inconsistent:**
  - User sessions, invites and device credentials are generated and hashed in httpapi via `accounts.NewToken/HashToken`, and only the hashes are passed to the store.
  - Agent session tokens are generated and hashed inside sqlitestore (session_tokens.go:39/56).
  - Gateway handles are generated and hashed in feishugateway and in connectors.
  - Service-tunnel tickets are hashed in httpapi (service_tunnel_auth.go).

  The session-token mint handler lives in session_timer_fires.go:122.

- **Identity has no protocol types.** Account/invite/member types live in web api-types.ts, unlike every other concept in this group (all of which are in packages/protocol).
- **Secret ids are plain-string conventions spread over packages** (`agent-profile:`, `external-app:`, `external-account:`, `external-login:`, legacy `feishu:app_secret:`), and there are four separate keeper interfaces (item 14). secretstore + sqlitestore/secrets.go is the only cohesive unit; the id namespace and the keeper interface have no single owner.
- **Profiles/accounts selection is spread across httpapi files:**
  - profiles.go (1058 LOC, mixes CRUD, promotion, projections, session profile resolution)
  - session_accounts.go and agent_defaults.go (account choice)
  - personal_agent_runtime.go (assistant run resolution, re-fingerprinting profile config at :301-340)
  - agent_model_catalog.go and secrets.go (credential overlay)

  Profile JSON normalization also exists in the worker profiles.ts (970 LOC) with different connection-type defaults (item 19).

- **Usage and quota have no single home.** Native log parsing is in the worker native-usage.ts. Live turn usage is in turn-usage.ts. Server backfill/merge is in httpapi/session_usage.go. Web summation is in chat feature files. Quota windows are in native-quota.ts plus two web fetch paths (items 22 and 23). Assistant token budgets are read separately in personal_agent_run_control.go:235.
- **The word "digest" names five things:** workspace digests (workspacedigest), daemon chat digests (daemon_chat_digests.go), the assistant's daily digest message (`sendAssistantDigests`, personal_agent_list.go:501), subagent digests (store/subagent_digest.go), and the "digest" session source. Workspace digest types are declared in store/personal_agent.go, not in their own store file.
- **Background-job registration is split** between lifecycle.go bare `go` calls and httpapi `integrationStarters` (item 10). Whether a loop honors `FOUNDRY_INTEGRATIONS=off` depends on which path it was registered through, not on what it does.
- **Candidates for shared modules, based on the duplicates above:**
  - a Go text package for token estimation, CJK detection and rune truncation (items 2-4);
  - a single "active session" predicate (item 5);
  - one gateway session-authorization function (item 6);
  - a typed device-RPC helper with a shared error-code→status table and protocol-declared capability constants (item 9);
  - one generic background-loop/queue runner (items 10 and 11);
  - one secret keeper interface plus a secret-id registry (item 14);
  - personal-agent defaults, policy presets and channel words, either served by the server or checked with a protocol fixture (item 1);
  - one loopback rule (item 18);
  - one usage-summation contract with fixtures (item 22).
