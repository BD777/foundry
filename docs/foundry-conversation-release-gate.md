# Foundry 对话式 Issue · 功能准出标准

[项目 Roadmap](../README.md#roadmap) · [Issue 工作流](issue-workflow.md) · [当前状态](current-status.md)

这是 **Foundry 产品功能的准出标准**：对话式 Issue、Evidence & Verify 与 Accept 相关的
产品改动，在宣称可用之前必须满足下面的 G1–G5。它不是某个测试 Issue 自身的验收契约。
设计与数据契约见 [Issue 对话与状态](issue-conversation-design.md) 和
[Evidence & Verify v1](evidence-and-verify-v1.md)；已实现边界见[当前状态](current-status.md)。

## 使用方式

- 做 Issue / Evidence 相关 UI 或流程改动前完整阅读本文；上下文压缩或换会话后重新阅读。
- 以本文衡量完成度：不能把前次摘要里的“已实现”当成验收通过，也不能缩减标准来迁就实现。
- 每次准出单独记录证据（截图、测试命令与结果、Issue/契约/判定身份、失败与修复），
  放在对应的变更说明或 PR 中，不写回本文。
- 历史验收只说明当时的结果；代码变化后需要重新验证，不把旧实测表述为新实测。

## 产品原则

用户表达意图和判断取舍，Agent 整理可执行的完成标准、提出验证方案，
系统执行真实采集与检查。用户不需要填写协议 JSON、枚举或七步表单。

- 主聊天是唯一对话入口：澄清、询问状态、参考上传、调整、执行反馈。
- Grill me 是发现歧义：每轮一两个有价值的问题，不重复已有信息，不把固定问卷念出来。
- 对话产出未确认的标准和取证方案；实际 Evidence 来自执行/观察/采集，不能由叙述冒充。
- Details 是“约定”；Evidence & Verify 是“兑现约定的证明”。
- Changes 和 Environment 是按需深入的信息，不是每个人的必经步骤。
- 用户看到自然语义；机器结构保留准确、可审计、不可绕过的版本与授权边界。

## 必须达到的行为

### G1 主对话与澄清

- 新 Issue 的原始输入成为首条对话；澄清是独立 Session，工作目录就是用户
  选中的 Workspace，能读目录、代码和项目说明，并据此提出有文件依据的建议。
  输入 `hi` 时回应目标问题，不生成通用完成条件、不启动实现候选。
- 澄清阶段只读：不改动源工作区文件、不写 Git、不产生实现候选；
  “未确认标准”限制的是开始实施，不是了解项目。
- 用户说“看看这个项目有什么值得改”时必须真的去看，不能要求用户贴目录或文件。
- 草案阶段从主输入框发送消息会收到 Agent 回应，而不是只保存为执行反馈。
- 发出消息后有发送/处理中/待回复/失败状态；失败说明原因，保留输入并可重试，
  不悄悄丢失消息、不自动重复执行未知结果的写操作。
- 询问状态得到阶段解释；“继续”不确认标准，不强行生成修订。
- 对话可上传支持的参考（文本/PNG/JPEG/GIF）；Agent 获取实际内容。
  不要求用户手抄 Material ID。参考不成为实际结果证据。
- 澄清采用已选 Harness/profile/model；模型请求只经过对应 Agent 的 SDK 或 CLI。

### G2 同源标准与显式确认

- Agent 提议保存为草案；聊天确认卡与 Details 从同一契约版本生成。
- 卡片用自然语言展示目标、每条完成标准、验证方法及重要范围约束。
- “确认标准并开始”绑定准确 revision/digest；过期卡片不能确认新的不可见内容。
- 信息不足时不能确认；单纯“继续”、普通聊天和状态问句不能代替显式确认。
- 已确认标准的调整需要生成新草案、展示改变和重新确认；执行反馈不默默改标准。
- 不要求额外的人工口令；聊天、参考、确认、验证和接受使用既有登录与权限入口。
- 标准与成果的用户决定沿用已有模型和准确版本绑定；Agent 只能提议草案，
  不能自行确认或接受。不另造设备信任、会话或自然语言授权判定系统。

### G3 信息架构与可读性

- tabs 上方保持“当前阶段＋下一步”。阶段变化给出入口，不抢切用户当前 tab。
- Details 按“任务目标 / 完成标准 / 范围与限制 / 参考与背景”分组卡片。
  空组隐藏，原始输入折叠，设备/仓库细节放 Environment。
- 每条标准表达“做到什么＋如何验证”；不用裸枚举、内部 ID、摘要作默认文案。
- 右侧没有第二聊天框、七步问卷及 JSON 主编辑流程；技术数据仅在按需展开区。
- 四个 tab 有清楚的职责和阶段空态；刷新及切换 tab 不丢失任务上下文。
- 桌面和窄屏可阅读、可操作，没有水平溢出/按钮遮挡/不可到达的输入区。

### G4 验收结果与真实证据

- 先展示整体结论、尚缺什么和下一步，再按完成标准展示结果。
- 每条标准显示实际观察、程序检查或独立 Agent 初判、依据预览与局限。
- 缺证据、失败、未知、过期分别解释“为什么＋影响＋怎么办”，不能只显示枚举。
- 所需材料和验证尽量由系统在明确动作后组织；端到端场景不能要求用户
  填 HTTP binding JSON、内部证据 ID 或手写验证协议。
- 实现总结不算 Evidence；材料缺失/候选变化/条件未通过时仍禁止 Accept。
- Verify 跑在本次实现的 Worktree 里，针对已封存候选版本实际查看成果、
  运行检查并采集证据；不是脱离项目、只读实现 Agent 叙述的文字评审。
- 验证前后都校验候选版本一致；验证过程不得改动候选，改动即判失败。
- 真实独立 Agent 判定至少覆盖一个候选文件场景，确认读取实际内容并有引用。
- Accept 必须显式批准准确 review；全部集成成功才显示 Accepted。
  历史结果和初判不被人工意见覆写。

### G5 回归与真实浏览器准出

- 补齐主对话路由、确认版本、展示映射、失败/重试、草案不派发的自动测试。
- 类型检查、相关 Web/Server/Worker 测试和生产构建通过；新增 UI 审计债务为零。
  既有失败需独立复现并记录，不能混称全量通过。
- 更新本机 Web 及必要的 Server/Worker；重启前检查活动执行，
  备份持久状态和配置。不能破坏不属于本测试的任务。
- 使用浏览器自动化操作真实页面，创建独立测试 Workspace/Issue：
  模糊输入 → 主聊天追问 → 参考/补充 → 自然语言草案 → 明确确认 →
  真实执行 → 采集/独立判定 → 可读结果 → 显式 Accept → 集成成功。
- 负向路径覆盖：未确认不执行、失败可见、缺证据不接受、过期结果不可复用。
  可组合自动测试和浏览器验收，但标明各自覆盖，不用 mock 冒充真实模型。
- 保存截图、测试命令与结果、Issue/契约/判定身份、失败及修复记录。
- 浏览器暴露不符合上述目标的行为，继续修复、重测，直到达标；
  若出现必须由用户解决的外部阻碍，明确报告，不能宣称完成。

## 不扩大的承诺

本标准不要求重写整个 Evidence 模型，也不扩大到通用浏览器自动采集、PDF/音视频、
任意外部服务依赖绑定或新的平台隔离。可以完整验证已支持的候选文本文件与本机能力；
未支持能力必须如实提示。不能因为不支持自动采集就退回要求用户填模型表单作为默认流程。

## 安全与工作区约束

- 保留所有已有 dirty worktree 改动，不自动提交、推送或清理。
- 不迁移、清理、重跑或接受不属于本次验收的既有 Issue；它们只作只读参考。
- 测试中的创建/确认/Accept 仅针对独立合成任务，说明由授权自动化操作，
  不伪称用户本人逐条点击。
- 真实采集、独立判断、准确版本确认、人工批准及安全集成门槛不得弱化。
- 不直接调用 provider 推理接口，不输出任何凭据。
