## 修复

### 1. 可靠发件箱的窗口（`packages/worker/src/transport.ts`）

- `bulkCredit`（单个）改为 `credits`：已写到 socket、服务器尚未确认的事件或分片（按 envelope id 或 `id#seq`），合计字节数小于 `pacedWindowBytes`（默认 32 KiB）时才写下一条；永远允许至少一条在途。
- 释放：envelope 确认（连同它的所有分片）、分片确认、服务器报错（`retryAfterError`）、换连接（`bind`/`unbind`）。来自旧 socket 的确认不释放。
- 30 s 未确认的 credit 不再计入窗口（防止丢失的确认让发件箱停住）。它只允许多写，**不会重发任何消息**；重发仍只在重连和原有的 5 分钟无应答检查时发生，服务器按 envelope id 去重。
- 小于一个分片（4 KiB）的普通 RPC 回复排在排队事件之前，只等窗口有空位，不再排在积压后面（本人设置时 20 s 超时的原因）。大的回复仍是 4 KiB 分片、与事件轮流。

### 2. 复用进程时不重连 Foundry 工具（`runner/foundry-tools.ts`、`runner/claude-runtime-start.ts`）

`claudeToolsNeedHandOver`：常驻进程仍服务同一个 Foundry 会话、新配置与持有的配置只差 `Authorization`、且持有的配置装上不到 20 h 时，不调用 `setMcpServers`。其他情况（换了会话、端点变化、没有记录时间、超过 20 h）照旧交接。

持有的令牌仍然有效的证明（`apps/server/internal/sqlitestore/session_tokens.go`）：同一会话的令牌在会话 queued/running/blocked 时一律有效；会话空闲时，距最后使用不超过 24 h 有效；只有在“空闲且超过 24 h 未用”时被解析才会删除；硬上限 30 天。最后使用时间不早于铸造时间，铸造早于装上，所以装上 20 h 内的令牌在会话空闲时也有效，不可能已被删除。常驻进程的空闲保留上限是 24 h（`activeRuntimeTtlMs`），超过 20 h 的复用会照常重连。服务器测试 `TestEarlierSessionTokenServesReusedProcess` 固定了这一约定（铸造 20 h 未用、会话空闲时解析有效；下一次派发铸造新令牌后旧令牌仍解析为同一会话）。

### 3. 排队的回合说明原因（`task-scheduler.ts`、`slot-wait.ts`）

调度器在任务不能立即开始时回调 `onWait({running, limit, sameKey})`。执行宿主和 daemon 两条路径都为该输入写一条事件 “Waiting for a slot”（中文界面“等待执行名额”）（“4 of 4 turns are running on this device; this turn starts when one ends…”；同一对话上一回合未结束时说明是在等它），开始时用同一 id 改写为 “Waited for a slot”（“已等到执行名额”）（等待时长、当时运行数）。Web 两种语言都有标签；等待中显示为进行中。服务器本身不限流，全部派发给设备，由 Worker 调度。

### 4. 并发上限默认按硬件（`device.ts`、设备设置）

- 本人未设置时：每 4 GiB 内存、每 2 个 CPU 各算一个回合，取较小者，限制在 1–16（协调会话因一台 2 vCPU / 2 GiB 设备把下限从 4 改为 1）。该设备（64 CPU / 252 GiB）为 16；2 vCPU / 7.5 GiB 的 dev 服务器设备为 1，但它已有本人设置 10，不受影响。小设备在设置页显示 “1 turn at a time on this device (N GiB memory, M CPUs)”。
- 本人设置的值总是优先；`FOUNDRY_MAX_CONCURRENT_TASKS` 视为本人设置。保存 0 表示撤回设置、回到硬件默认（服务器接受 0–16）。旧 Worker 收到 0 时按旧逻辑回到 4。
- `AgentRuntimeSettings` 新增 `maxConcurrentTasksSource`（`owner`/`hardware`）和 `hardwareMaxConcurrentTasks`。设备设置页显示当前值及来源：“按本设备硬件的默认值：N …” 或 “由你设置。本设备硬件的默认值是 N …”，并提供 “改用硬件默认值（N）”。
- 注意：已有 `runtime-settings.local.json` 中的 `maxConcurrentTasks` 按“本人设置”处理（以前的设置表单总是两个字段一起保存，所以只改过保留时间的设备也会被视为设置了 4）。设备页会显示 “由你设置”，本人可一键回到硬件默认。
- 改名：“活跃运行时缓存（分钟）” 易被理解为模型的提示缓存，改为 “空闲 Agent 进程保留时间（分钟）” / “Keep idle agent process (minutes)”，并说明：在这段时间内发送的消息会复用仍在运行的进程，启动更快；不影响模型服务商的提示缓存。

## 只等子会话的回合是否应让出名额（调研，未实现）

现状：一个回合调用 `wait_session` 等子会话时，它仍是一个运行中的调度任务，占一个名额；子会话如果在同一设备上，名额满时会排在它后面，可能形成等待链（父占名额等子，子等名额）。

如果让它让出名额：

- 资源：让出期间常驻的 Claude 进程仍在内存里（每个 Claude Code 进程常见几百 MB，含其 MCP 子进程），名额就不再反映内存占用；多个“等待中”的父回合加上新开始的回合可能超过硬件默认值所依据的内存预算。
- 重新获取：子会话结束、`wait_session` 返回时，父回合必须重新拿名额才能继续发模型请求；若名额满，父回合在工具调用中途被挂起，需要“工具结果已就绪但模型请求要排队”的新状态，并在对话里说明。名额的公平性（等待中的父回合优先于新回合）需要单独规则，否则父回合可能长时间饿死。
- 实现：调度器需要从“任务=整个回合”改为可在回合内释放/重新获取的租约；`wait_session` 在服务器上执行（MCP），Worker 需要从工具开始/结束事件判断“只在等待”，或由服务器通知。还要处理取消、超时与 steer 在挂起期间到达的情况。

建议：先不做。硬件默认值已经把大机器的上限提到 16，排队原因在对话里可见。若仍出现父子互等，优先做更小的改动：子会话派发到与父回合同一设备且名额已满时，允许超出上限 1 个（只对“父回合正在 wait_session 等待的子会话”），而不是让父回合让出名额。

## 更长的提示缓存寿命（调研，未实现）

官方文档：

- 默认缓存寿命 5 分钟，可指定 1 小时：`"cache_control": {"type": "ephemeral", "ttl": "1h"}`。价格：5 分钟写入为基础输入价的 1.25 倍，1 小时写入为 2 倍，读取一般为 0.1 倍（部分模型更低）；5 分钟写入读一次即回本，1 小时写入读两次回本。寿命从写入或读取它的请求开始时计算。中途从 5 分钟换成 1 小时会整段重写一次。来源：[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Pricing](https://platform.claude.com/docs/en/about-claude/pricing)。
- Claude Code：用户未指定时，只有在 Claude 订阅的包含额度内才请求 1 小时；用 API key 或云厂商时，设置 `promptCacheTtl` 为 `1h` 可让主对话使用 1 小时缓存。来源：[How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)。

对本例：两次请求间隔 8.8 分钟，1 小时缓存可以命中（读取约 21 万 token），代价是每次写入贵 0.75 倍基础价。是否值得取决于本人的停顿习惯和所用连接（订阅额度内 Claude Code 已自动使用 1 小时）。如需支持，可以作为设备或连接级的选项，在 Foundry 生成的 Claude 设置里写 `promptCacheTtl`；本事项不改。
