# DEV-034 · Authenticated local web services

Status: the same-site hardening increment is deployed to dev and enabled. The preview domain remains unset pending Cloudflare authorization, certificate/routing discovery and configuration. The actual 18082 service is explicitly registered and its executing Worker is updated, but public business-service browser acceptance is not complete.

## Requirement and observed gap

A running local web service should appear in Workspace Services and open in an ordinary browser after Foundry account authentication. Workers initiate outbound connections; visitors install no client and configure no SSH, VPN or inbound worker port. A URL alone grants nothing. Stopping access must not stop the business process.

The motivating service is a Compose-managed application on the `byte-dev` worker, listening on `127.0.0.1:18082`. Its development conversation belongs to a Mac workspace. The existing Services inventory lists registered persistent work, not arbitrary commands executed through SSH. No explicit service registration existed, so the empty overview was consistent with its inventory. Automatically inferring ownership by scanning ports or interpreting arbitrary shell history would be unsafe.

A web mapping therefore has an explicit display workspace and executing workspace/device. An existing managed process may be associated by work ID. An externally managed service has no invented stop/restart capability. Registration does not launch, reconfigure or replace it. Access requires current membership in both workspaces and ownership of the executing device for registration; private mappings do not inherit workspace-wide visibility.

This retains existing device identity/revocation, avoids bulk traffic blocking RPC/session traffic, and does not introduce a second tunnel daemon, user account or public listener on the worker.

## Implementation boundary

- `service_tunnels` stores explicit mappings under the existing Workspace Services surface. Target address is always `127.0.0.1`; only registered HTTP/HTTPS ports are accepted. No DNS target, arbitrary host, TCP/CONNECT mode or port scan is exposed.
- Source and execution workspaces are independently authorized. Only the executing device's owner can register. Sharing requires an explicit browser action; shared application access requires Member in both workspaces because application APIs may write business data. Admin role alone gives no access.
- `register_service` is the agent workflow for an existing service: verify actual device, executing workspace, protocol and port; register with a stable retry key; inspect returned readiness and URL. It creates only a private mapping. `list_session_work(workspaceId=...)` includes registered endpoints alongside existing process inventory. No manual database patch is part of the workflow.
- `FOUNDRY_PREVIEW_DOMAIN` names a dedicated preview site. Public Suffix List checks reject a site sharing the control plane's registrable domain. Each mapping has a unique application host. Preview hosts are dispatched before the control-plane router and never fall through to Foundry APIs/static files.
- A browser navigation obtains a short-lived, single-use login exchange through the Foundry origin. The ticket is POSTed, never placed in a URL. It is bound to browser state, the current login session, mapping/revision and account. Preview access uses a Secure, HttpOnly, host-only `__Host-` cookie; original Foundry session cookies, device headers and authorization headers are not forwarded upstream.
- Each request and WS handshake rechecks the original login, account, workspace roles, mapping and current device connection. Active streams recheck at five-second intervals with a three-second verification deadline, so authority loss is detected within eight seconds when storage is slow; uncertainty closes access. A separately bounded stalled downstream write can take up to another 30 seconds to release its socket. Mapping updates explicitly invalidate grants and streams. Device disconnect/replacement cancels its streams.
- Independent binary data sockets bound memory through stream backpressure and 32 KiB outgoing/64 KiB maximum frames. Limits are 128 total, 32 per device, 16 per mapping; uploads are capped at 64 MiB. Connect/header/TLS handshakes have time bounds. Response bodies are streamed without a fixed whole-response timeout. Each downstream write has a 30-second stall deadline; the deadline is cleared between writes, preserving healthy idle SSE/WS. Worker data channels also close after 90 seconds without server pings or data, even if the control socket remains healthy.
- Local HTTP redirects are rewritten to the application origin; other redirect origins are refused. Application cookies use encoded `__Host-` names; their original names/path scope are restored only on upstream requests. This prevents another application’s JavaScript from injecting parent-domain cookies, which Domain stripping alone cannot prevent. Cross-origin application requests and WS handshakes are refused. Service-worker registration is blocked to protect the exchange path. Foundry's main origin and other applications have separate DOM/storage origins.
- Internal HTTP listeners reserve protected ports in worker state. Old execution hosts do not advertise `service_tunnels_v1` until the protected-listener implementation is actually loaded. Busy hosts remain running; the UI reports the capability gap rather than pretending access works.

## Deployment gate and limitations

The current dev Nginx configuration and origin certificate cover `dev.foundryapp.app` only. A random sibling host resolving through Cloudflare and returning a response is not evidence of a usable, authorized preview deployment. A dedicated preview domain with wildcard DNS/TLS and ingress routing must be supplied/configured before public browser acceptance. No same-site path-proxy fallback is used.

Current compatibility boundaries: no anonymous/public URLs, no arbitrary destination hosts, no Web Workers or service workers, no emulation of JavaScript-managed `document.cookie` names, no externally redirected OAuth flow, no forwarding of application Authorization headers, and no automatic rewriting of hard-coded absolute URLs inside HTML/JS. Root-relative resources and APIs work; apps with hard-coded loopback URLs must expose a configurable public base URL. HTTPS upstreams require a trusted certificate valid for the loopback target. Grants are memory-resident and expire after eight hours or server restart; reopening uses the existing Foundry login.

Synthetic browser acceptance already exercised real login, anonymous and other-account denial, root-relative assets/API, WS/SSE, download digest, application cookie isolation, mapping revocation and reopening, registration, keyboard interaction and narrow light/dark layouts. These initial browser checks used a local TLS fixture. Remaining acceptance includes the final binary with production CSS, switching browser accounts without logout and recovering an expired preview cookie, additional readiness/error states, final Worker/Store gates, safe Worker update, dev deployment and read-only GET acceptance of the actual `18082` service. ## Operator and agent workflow

1. Configure a dedicated preview site with wildcard DNS and TLS. The ingress example is `deploy/service-tunnels.conf.example`; all paths, including assets and WS upgrades, must reach the Foundry Server with the original preview Host. Keep response and request buffering disabled. Set `FOUNDRY_PREVIEW_DOMAIN` on the Server. No control-plane cookie domain is widened.
2. Update the Worker through the existing update path. Confirm the actual execution host advertises `service_tunnels_v1`; an installed package version alone is insufficient. Keep busy old hosts alive until a safe transition.
3. In Workspace → Overview → Services → Web access, register the existing app's name, actual executing device/workspace, protocol and exact loopback port. Optionally associate a managed process. New mappings are private; sharing is an explicit checkbox and never grants a Viewer application write authority.
4. An authorized agent can instead call `register_service` with `workspaceId`, `targetWorkspaceId`, `name`, `port`, `protocol`, optional `workId` and a stable `registrationKey`. The CLI spelling is `foundry service register --workspace <display-workspace> --target-workspace <executing-workspace> --name <name> --port <port> --protocol http --registration-key <stable-key>`. Existing device-credential scope limits still apply; cross-device registration uses the person's browser account or an authorized session's workspace reach.
5. Open the mapping URL from Foundry. Another browser first signs in to Foundry. A copied URL gives no authority. Closing access revokes its streams but does not stop the application; re-enabling requires a fresh mapping grant.

Browser verification caught a concrete platform behavior: a `no-referrer` policy on the exchange form produces `Origin: null` for a form POST. The exchange page now uses origin-only referrers; no state URL or ticket is sent as a referrer. App responses use same-origin referrers so ordinary same-origin forms retain their expected Origin, while cross-origin requests remain refused.

The Cookie boundary is deliberately narrower than universal web-app compatibility. Same-name different-path cookies retain path precedence and independent deletion/expiry, while raw parent-domain cookies and encoded `__Host-` parent-domain injection cannot reach the upstream. An application's own Authorization requirement is distinct from Foundry authentication: the first release strips that header at the forwarding boundary, so such applications are explicitly unsupported rather than silently described as fully compatible. This is shown in the registration UI.

Additional official checks, 2026-10-21: [frp authentication](https://gofrp.org/en/docs/features/common/authentication/) describes `token`/OIDC authentication between `frpc` and `frps`; it is not, by itself, a Foundry browser authorization policy. [OpenSSH's manual](https://man.openbsd.org/ssh#R) specifies remote forwarding and bind-address behavior; reusing it would still require SSH credentials, remote listener management and the full browser authorization/origin layer. These are reasons to retain Foundry's existing outbound connection rather than provision a parallel transport lifecycle.

[Cloudflare's WebSocket documentation](https://developers.cloudflare.com/network/websockets/) explicitly distinguishes inspection of the initial upgrade from subsequent traffic, and notes that network releases can terminate connections. Its WAF statement is not a claim about Access policy revocation. Foundry therefore validates its own ongoing authority and treats disconnect/reconnect as normal; it does not infer continuous account enforcement from a successful 101 handshake or a vendor's general tunnel claim.

The actual `18082` service was independently checked through an authorized compute lease on its executing device: `GET /health` returned HTTP 200 with `ready: true`; the loopback Docker port mapping and Compose ownership matched the service owner’s report. The lease was released. This is direct health evidence only, not authenticated public-tunnel acceptance. No business POST, trial, configuration change or duplicate process was performed.

The user subsequently proposed reusing `foundryapp.app` with tenant subdomains. This changes the deployment design question; purchasing a second domain is not the only possible outcome. The current deployed guard still requires a separate site. The following is an audited implementation plan, not a claim that same-site mode is already supported.

A tenant-style address is reasonable as a Foundry-owned service index. The current authorization model is users, device owners and shared Workspaces, not a first-class tenant/organization model; a username must not become an implicit security boundary. Keep one canonical authenticated control origin initially. A future tenant alias can redirect to a filtered index there without becoming another trusted API origin. Do not add organization provisioning to this feature.

For actual application execution, use a unique first-level host such as `p-<opaqueMappingId>.foundryapp.app`, retaining the entire path namespace for that application. An index may use Workspace/service paths, but serving several arbitrary applications under those paths gives them the same browser origin. Sharing and owner renaming must not change a mapping's identity or its authorization. The server still checks the current user, both Workspace roles, device owner/credential, mapping revision and enabled state on every request and handshake.

Same-site mode needs a separate hardening increment before removing the PSL guard:

- Replace the control-plane login cookie with a Secure, HttpOnly `__Host-` cookie, Path `/`, no Domain. Ignore the old name completely in this mode; a legacy-cookie fallback would preserve sibling cookie injection. Plan an explicit one-time sign-in after migration, and test logout/account replacement against both old and new cookies. Preview/application cookies already use host-prefixed names.
- Admit only the exact canonical control Host and registered `p-` application hosts. Reject unknown hosts before any API/static routing; reserve control/portal names. A wildcard DNS match is not a valid service registration. Preserve device-only, no-Origin outbound data sockets as a separate authentication path.
- Preserve exact Origin checks for writes and WS. Add a cookie-authenticated GET/HEAD/WS provenance audit: current `sameOriginWrite` permits GET and `webSocketOriginAllowed` permits missing Origin. Reject sibling-origin browser API requests using Fetch Metadata where present, with narrow, documented exceptions for the nonce-bound top-level login exchange and state-validated callbacks. Non-browser callers cannot gain authority by forging these headers; they still need valid credentials. Review GET handlers for business/control side effects rather than relying only on CORS.
- Apply document-domain denial, origin-keyed agent clustering and opener isolation to the control UI as well as previews. Keep service workers blocked for previews. Do not trust every `*.foundryapp.app` Origin or widen control-cookie Domain. Test the browser behavior; headers alone are not acceptance evidence.
- Exercise malicious sibling cookie injection, legacy-cookie rejection, absent/null/foreign Origin, cross-origin navigation/embed, unknown Host, WS, expiry/revocation and account switching in the final same-site fixture. Existing separate-site browser evidence cannot substitute for these checks.

A hardened same-site deployment can target confidentiality and integrity between ordinary applications on supported modern browsers. It cannot provide the same availability isolation as a separate registrable site: malicious sibling scripts can still consume shared cookie quotas or inflate parent-domain Cookie headers, cause eviction/431 failures, and exploit broader same-site trust assumptions in future endpoints. Operators must also control all sibling DNS records and avoid abandoned third-party CNAMEs. These are explicit residual risks, not problems solved by a cookie prefix. A separate preview site remains the stronger isolation option.

Cloudflare configuration and authorization facts were rechecked against official documentation on 2026-10-21:

- [Wildcard DNS](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/) can resolve multiple hostname levels, subject to specific-record precedence; it provides no authentication. One wildcard installation is sufficient for mappings, so registering each service should not require a DNS API write.
- [Universal SSL limitations](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/) state that a full-setup zone covers the apex and first-level names. `p-id.foundryapp.app` fits that depth; `id.preview.foundryapp.app` does not without additional certificate arrangements. Confirm the actual zone setup and active certificate rather than inferring coverage from DNS.
- [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/) verifies an unexpired origin certificate with a matching hostname, issued by a public CA or Cloudflare Origin CA. The current origin certificate covering only `dev.foundryapp.app` is insufficient for the proposed application hosts.
- [Scoped API tokens](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) support resource restrictions, expiry and optional source-IP limits. For a one-time record operation, request DNS edit restricted to the `foundryapp.app` zone; zone read is only needed for discovering its ID. Certificate/settings operations require their own endpoint-specific permission and should not be bundled blindly. No Global API Key or secret pasted into chat is required.
- Contrary to an assumption based on older Cloudflare behavior, [OAuth applications](https://developers.cloudflare.com/fundamentals/oauth/) are now documented for all plans. [Client registration](https://developers.cloudflare.com/fundamentals/oauth/create-an-oauth-client/) supports Authorization Code, and PKCE S256 for public clients; third-party Device Authorization and Client Credentials flows are not supported. Scopes correspond to API permissions, and private clients are limited to members of the owning Cloudflare account. Creating a client still needs Cloudflare account permission and an exact redirect registration; documentation availability is not evidence that Foundry already has authorization. A complete Connector is optional future work, not a prerequisite for one wildcard setup.

The minimum configuration handoff is: confirm the zone/account and its full/partial setup; choose the single-level preview host pattern; supply a bounded authorized dashboard/API operation for the proxied wildcard without overwriting existing records; provision matching origin TLS and Full (strict); install exact ingress Host routing with unknown-host rejection, WS forwarding, streaming and query-free logs; then run public authorized/unauthorized acceptance. No DNS, certificate, Cloudflare OAuth client or API token has been created by this work. Same-site enablement remains gated on the hardening increment above.

The preferred address now expresses stable project ownership: `autorun.ws-<stable-workspace-id>.foundryapp.app`, with a separate origin per service and all paths left to the upstream application. The earlier flat `p-id` recommendation is superseded as the preferred presentation. The mapping's display/project Workspace determines the stable host namespace; its executing Workspace/device does not. Thus the Mac project Workspace remains the owner in the motivating case, while changing the byte-dev execution target does not rename the service. Workspace titles, membership/sharing and device relocation are not URL identity inputs.

A short Workspace label must be persisted with global collision checks, or use the full immutable Workspace ID; truncation alone is not an identity guarantee. Service names must use immutable reserved slugs or an opaque mapping suffix. Never silently reassign a retired application origin to another mapping: old localStorage/application cookies outlive a mapping's Foundry grant. Retain a tombstone/reservation, or issue a new mapping-specific hostname. Existing grants remain bound to mapping ID/revision and are revoked on target or authority changes. This does not introduce a tenant/organization model.

This preferred third-level layout requires real certificate discovery. In a full-setup Cloudflare zone, the default `*.foundryapp.app` edge certificate does not cover it. Possible configurations to assess are certificates for each `*.ws-id.foundryapp.app`, certificates for concrete application hostnames, or an already available Advanced Certificate Manager/Total TLS arrangement with verified wildcard/concrete-record coverage. `*.*.foundryapp.app` is not a valid general TLS wildcard solution. A partial/CNAME setup has different Universal SSL behavior per the official limitations page; do not assume that this account uses it. No paid feature will be enabled merely to satisfy the naming preference.
