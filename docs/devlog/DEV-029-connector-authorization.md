# DEV-029 Connector authorization and execution scope

Status: available on dev; final source submission/CI remains open. Agent self-verification and normal dev deployment authorized by the requester on 2026-10-21 via the coordinating session. This is not a report of human acceptance or completed deployment.

## Problem and verified execution semantics

The workspace device connector page listed every device owned by its viewer. Selecting a device did not move its credential or change session execution, but the UI looked like a shared credential pool. `connectors.DeviceEligible` requires the exact workspace, session device and device owner; `SessionUses` leaves an owner's own native login available even without a workspace binding. Binding removal is not an operating-system credential boundary.

`httpapi.sessionDevice` resolves explicit agents to their registered execution device; default account selection uses the workspace device. The workspace UI therefore defaults to its workspace device and offers another target only where an agent is actually registered to execute in that workspace. Global Connectors continues to manage all owned devices. Feishu remains server-held, under its existing account grants.

## Implementation

- Workspace device state and actions are scoped by a server-provided execution-device list. Cross-device new binding attempts are rejected; legacy bindings may be retained unchanged or removed, without silently moving credentials or switching workspace.
- Device authorization reuses the existing worker adapter and begin/poll routes. It checks native login first, serializes each physical login's authorization, supplies an opaque user/device/kind-scoped operation, deduplicates concurrent begins, throttles polls, expires challenges and rejects stale operations after a newer attempt or server restart.
- Completion requires a fresh native login read and a usable device state. This establishes local credential status, not a successful third-party business API call.
- Existing Feishu registration/authorization and device authorization share a typed challenge renderer. Only active HTTPS challenges expose a URL/QR. Secrets stay in their existing holder; the browser receives no CLI token.
- Workspace authorization binds only after completion, with explicit retry if binding persistence fails. Feishu connecting and reauthorization also open within the workspace, using the existing provider flows.
- Closing a dialog stops browser polling; the provider challenge expires normally. The CLI has no claimed cancellation capability. No automatic logout, account switching or credential migration.

No CLI package was downloaded, account switched, browser cookie read, provider grant started, business command repeated, or active execution host forcibly stopped.

The begin endpoint now returns a scoped operation receipt immediately. The same operation progresses through checking existing login, starting the native flow, awaiting approval and fresh verification. Each backend step has a bounded context; the Server's RPC budget includes one bounded FIFO predecessor. Worker status reads the independent login, authorization-group and package metadata checks concurrently after version discovery. A connector permits one running command and one queued command; installation is exclusive, with explicit busy feedback instead of an unbounded queue.

A lost transport response leaves the operation pending in its last dispatched phase. Retry checks that same operation: a possibly delivered native begin is reconciled by polling, never blindly replayed. Worker receipts retain the original PNG and pending challenge, and retain a completed receipt without its continuation secret until expiry. Fresh verification runs as a separate phase, so losing its response cannot consume a completed native token again. Closing revokes the browser resource and ignores late results; it does not claim to cancel a native provider request. Server/daemon restart makes unknown operation state explicit instead of inventing success. Base login and independent authorization groups remain separate.

Safe diagnostics record connector action, operation identifier, phase, queue wait and elapsed time. They exclude CLI arguments, provider response bodies, URLs, QR bytes, continuation tokens and cookies. Browser transport errors use an informational connection message; retry before the first receipt retains the original request id. Older responses without a phase field still display their existing challenge correctly.
