## 修复

### 服务器（`apps/server/internal/sqlitestore/session_work_changes.go`、`httpapi/session_work.go`）

- **变更序号**：`session_work` 新增 `change_seq` 列，另有单行表 `session_work_clock(seq, epoch)`。插入、更新（`payload_json`/`device_id`）和删除都由 SQLite 触发器取下一个序号。删除会在 `session_work_removed` 留下删除记录。用触发器有两个原因：交接期间旧二进制写同一个数据库时也会编号；工作区删除和孤儿清理用的通用 SQL 删除也会留下删除记录。迁移在一个事务里完成，加列、给已有行按 rowid 编号、建表、建索引和建触发器之间不会插进别的写入。
- **游标**：`<epoch>.<seq>`，epoch 是数据库建表时随机生成的。另一个数据库的游标、领先于当前序号的游标或格式不对的游标，都从头读取。读取在一个读事务里完成，所以同一项不会既出现在 `items` 又出现在 `removedIds`，游标也正好是这次读到的位置。一页读满时，游标停在最后一项，并带 `more: true`；没读满时，游标是当前全局序号。
- **路由**：`GET/POST /api/daemon/session-work?cursor=…` 先结算需要结算的项（记录过运行的定时任务，以及未确认结束或被要求停止的 Foundry 子会话），结算产生的写入会出现在这次读取的变化里。然后返回变化项、删除的 id、`cursor` 和 `more`。停止的线程、范围、`sweepRevision` 和覆盖范围仍然每次完整返回，它们都很小。不带 `cursor` 的旧 Worker 走原来的全量路径，行为不变。
- **结算不再空写**：`settleScheduledWork` 在运行和观察都没变时既不写运行也不写观察（运行已结束、而手动运行时间还没清除的情况照旧写）；`settleWorkChild` 只有时间不同时不写。

### Worker（`packages/worker/src/session-work/supervisor.ts`）

- 所有 `/api/daemon/session-work` 请求都带上游标，响应都并入本地清单：先清掉已确认送达的待发项，再并入，所以服务器回显的版本不会让刚发的项重新变成待发。处理 `removedIds`。游标和清单一起写进 `inventory.json`，重启后接着读。服务器不返回游标时（旧服务器）按全量处理，并在服务器升级后的第一次请求自动切换到增量。
- 首次读取分页进行；最多 1000 页。
- 对账时比较项的规范化 JSON，忽略 `observation.at`，键按排序。服务器存的观察字段顺序和新观察不同，最初的实现因此每轮仍重发全部定时任务（scratch 测量发现，已加测试）。
- 定时器从 `setInterval` 改为 `setTimeout` 链，间隔见上表。`setDraining(false)` 和本地观察（原生任务、定时器、子代理事件）都会唤醒对账。排空期间对账仍保持排期，不会停掉循环。
- `inventory.json` 内容没变时不写（dev 服务器设备上原来每 3 s 写一次 3.7 MB）。

## 跨重连与服务器交接的正确性

- **服务器交接**：序号和 epoch 存在数据库里，交接前后同一个数据库，游标继续有效。交接期间旧进程的写入由触发器编号，不会漏。
- **重连或执行宿主重启**：游标随 `inventory.json` 持久化，读到的变化会重复应用，而重复应用没有影响。保存晚于读取时（例如进程崩溃），会从旧游标重读。
- **换数据库**（scratch 副本、恢复备份后序号落后、全新数据库）：epoch 不同或游标领先时从头分页读取。同一 epoch 的备份恢复后若又写到超过设备游标，中间那段会漏读。这是已知边界，见“限制”。
- **删除**：工作区删除、孤儿清理和设备上的项都通过 `removedIds` 移除。

### Mac 台式机：`foundry-worker update` 0.3 s 以 0 退出、没有输出

- 只读排查：不是 PATH、更新锁、安装方式或 `release.json` 的问题——CLI 正确（`~/.foundry/bin/foundry-worker` → `.104`），没有锁，服务端 `release.json` 正常（同一台机器上用 `curl` 和 Node 自带的 `fetch` 都能读到）。
- 原因：这台 Mac 的 Homebrew `node` 已升级到 Node 26.0.0（内置 undici 8.0.2）。Worker 的 `serverFetch` 把 npm 包 `undici` 6.29.1 的 Dispatcher 交给 Node 自带的 `fetch`；undici 8 拒绝这个 Dispatcher（`UND_ERR_INVALID_ARG`），而 Worker 的 `ServerDispatcher` 把错误交给 undici 8 已不再调用的 `onError`，于是请求永远挂起。之后没有任何句柄让事件循环继续，进程直接以 0 退出，也不打印任何内容。`update` 卡在询问服务器版本这一步（`serverWorkerRelease`）。在设备上用最小脚本复现：`serverWorkerRelease` 永不返回；同一请求用 npm `undici` 自己的 `fetch` 正常。
- 影响：daemon 从 10-27 起一直运行 `.81`（较早、不经过这条路径），已安装的 `.104` 和之后的版本在 Node 26 上无法向服务器发 HTTP 请求。daemon 一旦重启（升级、重启机器、看门狗），会以 `.104` 启动，向服务器的 HTTP 请求全部挂起。
- 修复（`packages/worker/src/server-proxy.ts`）：`serverFetch` 改用同一个 npm `undici` 包的 `fetch`，Dispatcher 与 fetch 版本总是一致，与 Node 自带的 undici 版本无关。测试 `server requests do not go through Node's bundled fetch`：把全局 `fetch` 换成永不返回的函数，`serverFetch` 仍然成功；在旧代码上该测试挂起。在 Mac 台式机 的 scratch 目录里用新包 + Node 26 运行 `serverWorkerRelease`，立即返回新版本（只读，没有改动安装）。
- 更新：确认这台设备上没有运行中的会话（本人的会话已结束）后，用新包的 CLI 执行一次常规 `update`。daemon 重启到新版本并重连，执行宿主空闲，随即切换。之后在该设备上用已安装版本、Node 26 调用 `serverWorkerRelease` 正常返回。scratch 目录和日志已删除。
