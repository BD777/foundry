# IM 接入、账号权限与平台扩展设计

[项目 Roadmap](../README.md#roadmap) · [文档索引](README.md)

本文分别说明 IM 接入、账号与权限体系、云端 Workspace 和 Workflow 插件化。完成状态统一维护在 README；末尾未排期探索仅保留背景，不作为当前实施要求。

IM 接入提供额外交互入口，单人使用也有价值；账号与权限体系管理 Foundry 自身的身份、团队成员和授权。两者的衔接点是 IM 身份映射到 Foundry 账号，以及所有入口使用相同权限判断。两者可以并行推进，IM 开放的每项操作都走同一套身份与权限判断。

IM 与账号权限不依赖云文件系统，可以和云端 Workspace 工作并行。远程文件语义和插件选型按真实需求验证，不作为当前工具与证据链的前置。

## IM Integration

**现状：** 已有飞书专用实现（`apps/server/internal/feishu`），尚未抽出通用 Adapter。每个 Workspace 配置自己的 Bot，经长连接接收事件，不需要公网 IP；群通过一次性配对码绑定 Workspace，群内话题映射为 Chat 会话，回复以流式卡片更新，话题内跟帖无需再 @Bot。群以生成配对码的账号身份执行，每条消息都重新校验该账号在 Workspace 中的角色（见[安全边界](security.md#accounts)）。话题对应 Issue、按发送者本人授权仍未做。

**交付目标：** 通过通用 Bot Adapter 接入 IM，使用户能够发起、跟进和回应同一 Issue，复用 Foundry 的任务状态、账号与权限。MVP 只接飞书（Lark），支持个人或团队使用。

**接下来做：** 先定义通用的入站事件与出站动作契约，覆盖用户身份、会话、消息或回复关联、附件、交互回应及事件标识。Foundry 的任务逻辑使用这层契约，由 Adapter 转换具体平台协议。优先评估业界通用 Bot 协议的复用范围，具体协议与库尚未选定；保留平台能力差异，不假设所有 IM 都有相同的 thread 或交互语义。

在此基础上实现 Lark Adapter，打通 Workspace—会话和 Issue—消息上下文映射、任务发起、进度通知与 Ask user 回应；建立 Lark 身份与 Foundry 账号的绑定、校验和解绑流程，按该账号的权限处理操作与消息可见范围。Slack / Telegram 等留作后续适配，不进入 MVP 范围。

通用协议的复用是选型目标，不是已确定存在一个兼容所有平台的协议。实现前核对候选协议与 Lark 的实际支持范围；保留平台及租户作用域的身份和消息标识、请求真实性校验与幂等处理。普通消息、交互回应与内部任务控制保持明确边界。

**完成标准：** Lark 经 Adapter 与 Web 操作同一任务，核心任务逻辑不直接依赖 Lark 消息格式；IM 操作可归属到明确的 Foundry 账号并沿用其权限；未绑定身份、无权限操作及重复事件有明确处理，解绑后旧映射失效。群成员身份不会自动授予 Workspace 或 Accept 权限，通知与材料不超出接收者的授权范围。复杂审阅可回到 Web，是否在 IM 内直接 Accept 仍待决定。

依赖稳定 Issue 语义及账号与权限体系的最小身份映射、授权契约，不要求完整团队功能先完成。

## Accounts and Permissions

**现状：** [账号与权限设计](accounts-permissions-design.md) 的 P1（身份与隔离）和 P2（Workspace 共享）已落地：所有接口要求登录，设备凭证与资源归属，读取按调用者过滤，Workspace 按 Viewer / Member / Maintainer / Owner 共享，Agent token 继承发起账号的权限。P3（个人连接授权、飞书身份绑定）、P4（审计、所有权转移）和设备密钥对认证未做。

**交付目标：** 建立 Foundry 自身的账号、登录身份、团队成员管理和权限体系，为 Web、IM 及后续托管服务提供统一身份与授权依据。

**接下来做：** P3——个人连接授权给 Workspace、协作者执行凭证按发起人解析并记录来源、飞书用户与 Foundry 账号绑定并按发送者本人授权；P4——成员与授权变更的审计视图、所有权转移，以及设备密钥对认证。设计见[账号与权限设计](accounts-permissions-design.md) §3.1、§8、§9。

**完成标准：** 各入口对同一账号执行一致的授权判断；成员或权限变更后访问按新授权生效；未授权账号不能读取受限内容、使用执行资源或接受变更；关键操作可追溯。仅具备聊天或创建 Issue 权限，不意味着具备 Accept 权限。

本项独立于 IM 接入；IM 可先依赖已有的身份与权限契约推进。

## Cloud Workspace

**交付目标：** 托管 Workspace 本身的项目文件、内容与持久状态，让不同执行端按权限访问同一个逻辑文件系统，并以其中已接受的状态作为项目基线。

**接下来做：** 定义 Workspace 身份、文件与目录访问、候选版本、接受写入和恢复的契约，验证本地或远程 Daemon 如何获取对应状态并执行读写、构建和测试。远程访问、缓存或同步必须关联正确候选，多个任务仍经隔离、验证与 Accept 更新 Workspace。

这里的“同一个文件系统”指同一个逻辑 Workspace 和权威状态，具体采用挂载、文件接口或候选快照仍待验证。本项范围是 Workspace 存储与访问；托管 Agent、供应执行机器或代管 Provider 运行环境不属于本项要求，也不是它的前置。

**完成标准：** 更换或断开执行端不会丢失已接受的项目状态；授权执行端可取得正确版本并提交候选变更；并发与恢复不会让旧副本覆盖新的权威状态；本地和远程访问遵守相同候选、验证和接受语义。

依赖 Workspace 身份、文件与版本边界、权限及恢复契约；不预先绑定某种分布式文件系统。

## Workflow Plugins

**探索，未排期。** Issue 的准出条件 → 执行 → 验证 → 接受这一套，本质上是一种 Workflow。不同的人组织工作的方式不同，Foundry 不应把一种流程强加给所有人。设想是先把本体（Workspace、Sandbox、会话、账号与入口）做稳，再把 Workflow 做成插件：Issue 作为内置 Workflow 随产品提供，同时开放扩展接口，例如在侧边栏增加 Tab、定义自己的 Workflow 与视图。

Issue 仍是已商定的主线方向，无论最终是内置插件还是内置功能，都不改变它的语义和完成标准。插件接口的形态、权限边界和参考对象尚未调研，出现具体需求前不建立通用插件框架。
