# Where things live

Read before changing protocol types, contracts, Server routes or storage, MCP tools, the Worker or the Foundry skill, and before running checks or scratch stacks. Pointers, not specs; read the code first. Paths from the repo root. Web pointers are in `apps/web/AGENTS.md`.

## Code

- Protocol types in `packages/protocol/src/`; consumers read `dist/`, so run `pnpm --filter @bd777/foundry-protocol build` after edits.
- Contract (OpenAPI 3.1, single source for migrated types): `contracts/` (root `foundry.openapi.yaml`, models in `models/*.yaml`); `pnpm generate:contracts` writes the TS types, Go models (`store/*_gen.go`) and JSON Schema; never edit generated files. Plan: `docs/refactor/phase6-openapi-design.md`.
- Server: routes in `apps/server/internal/httpapi/routes.go`, each with an access rule; routes a session token may call are marked `agent(...)` in `routeTable` (`onlyAgentRoutes` in `policy.go`); MCP tool schemas in `httpapi/mcp_tools.json` (embedded), handlers `mcp*.go`. Store: `internal/store/` (interfaces, models), `internal/sqlitestore/<area>.go` with `setup<Area>` migrations; every `foundry-server` run migrates its DB, so always set `FOUNDRY_DB_PATH`.
- Worker: `packages/worker/src/cli.ts` (`foundry-worker`), `foundry-cli.ts` (`foundry`), `daemon-connection.ts` (server link). Bare `node --test` writes into the real `~/.foundry`: test in `packages/worker` with `node scripts/run-worker-tests.mjs -- <f>.test.mjs`.
- Foundry skill: `packages/worker/skills/foundry/` = `apps/server/internal/builtinskills/foundry/`, byte for byte (`packages/worker/test/foundry-skill.test.mjs`). Docs: `docs/`.

## Checks and stacks

- Verification data isolation: never create test connector instances, channels or other data in the person's account. Use `e2e-alice` or a scratch stack, and remove scratch resources when finished.
- Orchestrating sub-sessions: small fresh slices, context and test discipline, shared heavy-command lock, merge rules: [docs/agent-orchestration.md](docs/agent-orchestration.md).
- Testing scope: during implementation and review run only `-run`-targeted Go tests, named single test files, and at most one project typecheck. Do not run a whole package, `go test ./...`, full `pnpm test`, `pnpm verify`, or `-count=1` unless the request calls for that scope. Run the merged batch check once at commit time; release work alone uses the full verification suite.
- Classify commands before running them. Light commands (`prettier` on the touched files, `gofmt`, `go vet` on one small package, one small JS test file, audits) run directly on sg-chaos without the heavy lock. Heavy commands (project-wide `tsc`, Vite build, `go build ./...`, `go test` of large packages such as `internal/httpapi`, Worker packs) go to a remote runner first.
- Runner order is CanWendeMac-mini → byte-dev → byte-dev-sg. Both scripts accept `--device mac|byte-dev|byte-dev-sg`, `--resource <res_…>`, a positional device/resource, or a handed-over lease; a preferred alias falls to the next online runner. Device acquisition is shared by default; set `REMOTE_LEASE_MODE=exclusive` only when one job must own the whole device. A Foundry session uses `acquire_resource {resourceId or type: compute, deviceId, mode: shared, forCommands: true, holdFor: 3600}` on the first online runner, then runs in the background with `L=<leaseId> T=<commandToken>`:
  - `FOUNDRY_LEASE_TOKEN=$T scripts/remote-check.sh $L [--tree <worktree>] --go ./internal/httpapi -run 'TestA|TestB'` (or `--web typecheck`, `--web test test/x.test.mjs`, `--worker test x.test.mjs`, `--files <paths>`, `--sh '<line>'`). It sends everything differing from the tree's pushed base, prints failures and the output tail, and writes the full log to `/tmp/remote-check-*.log`.
  - `FOUNDRY_LEASE_TOKEN=$T scripts/remote-build.sh $L --out <empty dir> [--tree <dir>] [--server] [--web] [--worker]`: linux/amd64 Server, Web `dist`, and Worker packages with `SHA256SUMS`; `--fetch-only` fetches the device's last build after a failed transfer.
  - All runner state is under the removable compute scratch root `~/.foundry/compute/foundry-remote`. Every invocation gets its own `jobs/<id>/repo` checkout; the toolchain (`node`, pnpm, Go) and Go/pnpm/npm caches are shared below the same root, so jobs do not overwrite each other and caches stay warm. If Node ≥22, pnpm, or the Go version in `apps/server/go.mod` is missing, the script bootstraps it there without a system install.
  - Runners are concurrent. A counting slot guard, not a lock, limits active jobs to `min(CPUs / 2, GiB / 4, 16)`: CanWendeMac-mini 4, byte-dev 16, byte-dev-sg 3. Jobs never take `/tmp/fdy-heavy.lock`. `remote-build` runs Server, Web and Worker side by side; Go builds/tests use their job's CPU share (`CPUs / slots`).
  - Several checks from one session may use one lease concurrently: start each with `REMOTE_KEEP_LEASE=1` and the same `FOUNDRY_LEASE_TOKEN`/lease id, then release the lease once the batch is done. A remote-check job checkout is removed when it finishes; build jobs stay until batch cleanup so `--fetch-only` can recover a failed transfer.
  - Set `REMOTE_HTTPS_PROXY` only for a runner that needs a local egress relay. Without it, the script probes byte-dev's `http://127.0.0.1:12263` and uses it only when that relay reaches `proxy.golang.org`.
  - At the end of each work batch, remove that session's job directories: `FOUNDRY_LEASE_TOKEN=$T scripts/remote-clean.sh $L`, or `--device …` / `--all` outside a Foundry session. The default never touches shared caches, toolchain, or another session's jobs. For a final handback of a borrowed runner, add `--root` (or `--all --root`) to remove the whole shared root; this refuses while any job slot or live job is active. Every mode lists leftover Foundry-named paths under the runner's home and `/tmp`.
  - Without `REMOTE_KEEP_LEASE=1`, each remote script releases its lease when it ends. A waiting session takes the lease 15 minutes after it began waiting, so keep one run under that.
- Shared one-shot lanes use `scripts/fdy-lock heavy|deploy [--wait <seconds>] -- <command>`. It maintains FIFO tickets, records holder pid/session/command/start time in a `.holder` sidecar, prints position and elapsed time every 30 seconds, reports stale holder pids, and appends wait/run records to `~/.foundry/server/lock-log.jsonl`. `scripts/fdy-lock status [heavy|deploy|all]` shows holder and queue. `/tmp/fdy-heavy.lock` exists only for work running on sg-chaos's 2 CPUs; remote-check/remote-build never take it, including local sync, fetch and cleanup. Use it there only as the last resort after remote runners are unavailable; never wrap a long-lived server or its parent shell.
- Deploy prebuilt artifacts: `scripts/deploy-dev.sh --prebuilt <out> --label <item> [--server] [--web] [--worker]` takes `/tmp/fdy-deploy.lock` through `fdy-lock` itself (do not wrap it in flock) and refuses `--build`. Build first with `remote-build.sh`; the deploy lock covers only the swap. It keeps `.pre-<item>` copies, swaps Server/Web/Worker and rolls back a failed step. Devices then update with `update_worker`. `remote-build.sh` records `SOURCE_MANIFEST` plus its hash in `build-info.txt`; before swapping Server or Web, `deploy-dev.sh` refuses an artifact that omits live source. After verifying an intentional replacement, name the live id with `--replaces <current-build-or-server-sha>`.
- Scratch stacks (optional): `scripts/scratch-stack.sh up|shot|down <name>`. A server on a DB copy acts on its integrations (a second Feishu bot, Connectors refreshes rotating real tokens) unless `FOUNDRY_INTEGRATIONS=off`, which the script sets.
