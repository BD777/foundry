## 1. 产品定义与核心价值

### 1.1 一句话定义

**已确认。** 这是一个围绕 Workspace 组织 AI 工作的生产工具：人提出目标和完成标准，Agent 在隔离环境中执行、验证并提供证据，人决定接受或放弃，接受后的变更回到同一个 Workspace。

它首先来自创始人自己的 AI 工作流，而不是先选择一个 Agent 概念再寻找应用。项目已有第一个版本，尚未开源；希望在 Evidence 与 Acceptance 的核心闭环完成后进入可开源阶段。

### 1.2 为什么以 Workspace 为中心

Workspace 首先是一个文件系统目录。选择这一形态的原始理由是：目前接入的 Agent 工作方式围绕一个 CWD 及其可访问的文件、命令和环境展开。产品因此不把某一段 Chat 当作全部资产，也不把产品绑死为一个代码仓库管理界面。

Workspace 容纳正在构建的东西，也容纳帮助后续工作更好完成的东西，例如代码、文稿、PPT、数据文件、测试、脚本、操作说明和项目约定。

**自我演进的含义是资产和可复用工作能力持续积累，不是 Agent 未经批准改写自己的权限，也不是宣称模型权重在自动训练。**

### 1.3 人被放在流程两端

左端是输入：提出 Idea、功能、Bug、优化点或其他数字化目标，并与 Agent 一起明确怎样才算完成。

右端是准出：查看变更与 Evidence，判断是否满足目标，接受进入 Workspace，或决定放弃该 Issue。

中间仍允许人 steer、回答问题和补充约束，但设计目标不是让人持续盯住 streaming、挽救每次底层报错或管理技术性执行会话。

### 1.4 目标与非目标

**目标：** 提高 Agent 有效吞吐率，减少不必要的串行等待，让人管理意图、约束和结果，而不是执行基础设施；同时保护 Workspace 这一最重要的资产。

**范围：** 软件工程是当前最自然的切入点，但长期不局限于代码。只要交付可以用文件或数据表达，例如老师备课、文档处理、PPT 制作、数据加工，都可以进入相同工作框架。

**当前不要求：** 自研通用大模型、自研更强的完整 Harness、面向用户建立复杂的 Run 管理系统、建立独立 Asset 商品库、在第一版完成分布式文件系统或完整企业平台。

### 1.5 产品闭环

```text
Workspace 的当前可信状态
        ↓
人提出 Issue，并确认目标与准出条件
        ↓
Agent 在隔离候选环境中执行；必要时阻塞、求助、恢复
        ↓
工具与环境产生 Evidence，验证器给出判断
        ↓
人审阅目标、变更、证据与判断
        ↓
人决定接受 → 排队、对齐最新状态、复验、合入
        ↓
Workspace 获得新的产品内容与可复用工作能力
```

若人决定放弃，候选变更不进入 canonical Workspace；执行记录与证据的保留、清理属于独立策略。

## 2. 当前产品形态与实现现状

以下均为**现状陈述**，来自用户在本次对话中的介绍。

| 方面           | 已描述的实现                                                     | 本文不据此推断的内容                           |
| -------------- | ---------------------------------------------------------------- | ---------------------------------------------- |
| 产品界面       | Web 产品；已经完成 Chat 的第一版                                 | 不推断所有浏览器、移动端或多人场景都已兼容     |
| Chat 体验      | 参考 Codex Desktop 的 Chat 体验，集成类似的 subagent 展示        | 不推断复用了哪些具体源码，也不推断其授权情况   |
| Agent 接入     | 已通过 SDK 接入 Codex、Claude Code 等现成 Harness                | 不推断各适配器功能完全一致                     |
| 执行位置       | 用户宿主机运行 Daemon；Agent 在该执行侧运行                      | 不推断已经完成分布式调度与容灾                 |
| Workspace 位置 | 跟随 Daemon 所在侧的文件系统，不在中心 Server 内                 | 不推断已经实现远程挂载或云端存储               |
| Workspace 接入 | 可以从任意目录开始；不是 Git 仓库时进行 `git init`               | 不推断已有未提交文件、嵌套仓库等边界均处理完毕 |
| 多仓库         | 递归发现子仓库；按 Issue 涉及的仓库创建 worktree，组织 Agent CWD | 不推断多仓库具有原子提交语义                   |
| 并发执行       | 使用 Git worktree 隔离多个 Issue 的候选变更                      | 不将文件隔离等同于进程、网络、凭证或设备隔离   |
| 人工接受       | 人确认接受后，将候选变更合回原 Workspace 所对应的目录/分支       | 不推断 merge queue、rebase 复验已实现          |

### 2.1 当前架构理解

```text
浏览器中的 Web UI
        ↕
产品 Server / 控制面
        ↕
用户宿主机上的 Daemon
        ├── Codex / Claude Code 等 Harness
        ├── Workspace canonical 目录及相关仓库
        ├── 各 Issue 的隔离 worktree / 候选目录
        └── 本机工具、服务与可用资源
```

控制面具体存储什么、使用何种通信协议、如何部署，尚未在对话中定案。

### 2.2 Chat 为什么仍然重要

**已确认。** 当前实际工作仍需要自然语言沟通、补充上下文和 steer，因此 Chat 是必要的交互基础，而不是应该被消灭的过渡界面。

但 Chat 不是完成状态的唯一展示面：用户不能为了决定是否接受而必须从很长的对话中自行寻找证据。结果审阅应有独立、结构化的视图。

独立 Chat 与 Issue 是否共用全部数据模型、是否支持一键从自由聊天生成 Issue，属于待决的交互细节。

## 4. 核心概念与边界

### 4.1 最小领域词汇

| 概念                        | 含义                                                     | 是否需要成为独立用户对象               |
| --------------------------- | -------------------------------------------------------- | -------------------------------------- |
| Workspace                   | 经接受的文件与数据所构成的持续工作空间，以及其项目上下文 | 是                                     |
| Issue                       | 人提出的目标、约束、准出条件及围绕该目标的持续工作       | 是                                     |
| Acceptance Criterion        | 某个 Issue 的一条完成条件                                | 需要可识别、可审阅；不强制顶层导航     |
| Evidence                    | 针对完成条件提供的可检查材料及其来源、状态关联           | 需要明确模型与展示                     |
| Verification                | 对条件及其 Evidence 作出的判断                           | 必须与原始 Evidence 区分               |
| Acceptance                  | 有权限的人基于变更、证据和策略作出的接受决定             | 是一个关键动作与记录，不一定是顶层对象 |
| Resource                    | 执行或验证需要的可申请能力/环境实例                      | 是底层能力；按需向用户呈现             |
| Change / Diff               | Issue 对 Workspace 提出的候选文件变更                    | 需要审阅，不要求另造 Asset             |
| Harness Adapter             | 对接某种 Agent Harness 的适配层                          | 内部实现概念                           |
| Session / Attempt / Handoff | 底层会话、恢复尝试、交接等运行细节                       | 不作为用户必须理解的独立对象           |

### 4.2 为什么没有独立 Run

一个 Issue 可以像可恢复的持续会话一样工作：中断后继续，回答用户问题后继续，底层更换 session 后也继续。

是否有一对多的内部执行记录，是实现选择；**不能据此要求用户创建 Run、挑选 Run、关闭 Run 或理解“这次是新的 Run”。**

调试界面可以提供“执行历史”“恢复记录”，但主体界面仍围绕同一 Issue。底层会话 ID 可以用于证据追踪，不应成为证据必须由用户填写的关联字段。

### 4.3 为什么没有独立 Asset

产物可能是新增文件、删改文件、代码、文稿、PPT、图片或二进制文件。它们都可以属于 Workspace 的内容变化。

“产品资产”和“能力资产”有助于理解自我演进，但不构成两套额外生命周期。脚本与业务代码一样，可以通过 Issue、验证和接受进入 Workspace。

**工程补充：** “都能作为文件”不等于“都能展示为逐行文本 diff”，也不等于“目录中的所有文件都已由 Git 跟踪”。二进制预览、大文件存储和 ignored/untracked 文件需要明确策略，不能依赖一个文字 diff 页面兜底。

### 4.4 Single Source of Truth 的准确含义

已确认的是：**被接受的产品状态以 canonical Workspace 为准。** 不因此强制所有日志、Chat 事件、临时截图或凭证都进入代码仓库。

**建议草案：** 产品内容、持久上下文、运行元数据和证据 blob 可以有不同物理存储，但必须有稳定关联与导出策略。另建元数据存储不能让数据库里出现一份与 Workspace 冲突的“已交付产品状态”。具体持久化布局尚未定案。

## 5. 用户体验与完整工作闭环

### 5.1 从提出意图到开始工作

用户选定 Workspace，提出功能、Bug、优化或交付目标。Agent 可以帮助澄清、建议准出条件及材料形式，但开始执行前由人确认必要的目标与证据要求。

第一版不必强迫用户填写大量专业表单。可以让自然语言输入生成一张可编辑的完成清单，再由用户确认。

### 5.2 执行期间

Agent 使用现有 Harness，在该 Issue 的候选目录与授权环境里工作。可以调用工具、申请资源、生成中间产物、做测试和自我修正。

用户可以查看 Chat、subagent 活动、关键进度和阻塞原因，但无需持续在线。系统应尽可能自动处理短暂错误；只有需要人的信息、权限或取舍时才明确请求介入。

### 5.3 审阅时

**建议草案。** 结果页以“目标—条件—证据—判断”为主，至少让人直接回答：

- 这次准备改变什么，涉及哪些文件或仓库？
- 哪些准出条件通过，哪些缺证据、不确定或已过期？
- 证据来自哪里，绑定什么候选版本？
- 接受后会进入 Workspace 的到底是什么？

Chat 保留为上下文与追问入口，而不是唯一审阅工具。

### 5.4 审阅后的动作

人可以接受、要求继续修改、补充说明或放弃。要求继续修改不是创建另一个 Issue，也不是宣布前一个 Run 失败。

人点接受之后仍须经过合入保护。若排队期间 canonical state 改变，系统需要对齐、复验；出现实质变更时是否要求重新确认，按第 11 节的建议策略处理。

## 6. Issue 生命周期与恢复语义

### 6.1 产品层原则

**已确认：** 不因为某次 API 错误、机器离线或执行中断，就给 Issue 一个不可恢复的 Failed 终态。

工具调用可以失败，测试可以 fail，重试可以耗尽；任务仍保留同一 Issue 与恢复上下文。后续讨论明确：系统可自行处理的问题保持自动恢复或等待，只有确需人提供信息、决策、授权或手动处置时才进入 Blocked。

### 6.2 状态表达草案

**2026-09-09 后续纠正：** 当前实施收敛为 Pending / In progress / Blocked / Verifying / Accepted / Abandoned 六个顶层状态。Blocked 带 `needs_input`、`needs_permission`、`system_error` 等具体原因；不另设 Interrupted 顶层状态。下表保留最初讨论中的细分阶段，其中 Ready for Review、Queued / Integrating 归入验证/合入进度。实现与兼容规则见 [Issue 对话与状态](../issue-conversation-design.md)。

以下是**建议草案**，状态名称可以按现有系统调整，不是已冻结的数据库枚举。

| 状态                 | 用户语义                                             |
| -------------------- | ---------------------------------------------------- |
| 待确认 / Ready       | 目标与准出条件准备中，或已确认等待执行               |
| Working              | Agent 正在处理这个 Issue                             |
| Blocked              | 需要人介入；说明具体问题、需要谁回应及回应后如何继续 |
| Verifying            | 正在采集证据或检查完成条件                           |
| Ready for Review     | 候选结果和审阅材料已准备好                           |
| Queued / Integrating | 人已表达接受意愿，正在等待或进行最终集成             |
| Accepted             | 按最终定义完成接受；建议仅在成功合入后显示为最终完成 |
| Abandoned            | 人明确决定不再继续                                   |

`Queued / Integrating` 可以作为 Issue 上的进度阶段而非新增顶层状态。**“人已批准”与“已成功合入”必须能区分，但是否拆成两个持久状态仍待实现设计。**

```text
Ready → Working ↔ Blocked
           ↓  ↑
        Verifying
           ↓
     Ready for Review ──要求修改──→ Working
           ↓ 人决定接受
     Queued / Integrating ──需处理问题──→ Blocked / Working / 重新审阅
           ↓ 成功合入
        Accepted

未完成的 Issue ──人决定放弃──→ Abandoned
```

### 6.3 Blocked 必须有原因

Blocked 专指需要人介入，例如 Ask user、业务决策、授权或人工修复。应明确请求内容、对应 Issue、回应是否仍有效及继续入口；人回应后沿原 Issue 继续，其他独立 Issue 可继续运行。

等待共享资源、短暂离线、自动重试和系统可自行恢复的错误不属于 Blocked，应记录其实际进度或等待原因。配额、冲突或环境错误是否进入 Blocked 取决于是否需要人行动，不按错误类型一律归类。具体内部状态名和恢复流程仍待实现设计。

### 6.4 恢复与重试

短暂错误由内部重试吸收；重试耗尽后保留同一 Issue，说明发生了什么并允许恢复。断线后恢复应检查已有文件、进程、资源租约和已完成动作，避免盲目重放有副作用的命令。

**建议草案：** 设置自动重试与预算边界。到达边界后保留可恢复上下文；如需要人提高预算、授权或修复环境，提供具体请求并进入 Blocked。系统仍可自行恢复或等待时不标成人工阻塞。用户期望“持续做到完成”，不应被实现为“不受约束地无限重试”。

### 6.5 接受、放弃与自动化边界

Agent 可以提出“该需求可能已过期”“缺少条件无法继续”等建议，但不能自行放弃。第一版不实现自动接受；未来的 auto-accept 只作为曾讨论的可能方向，必须另立策略与授权决策。

已接受 Issue 是否支持 reopen、已放弃候选保留多久、恢复后是否继续使用原 worktree，尚未定案。

## 7. Acceptance Criteria：完成标准

### 7.1 三层模型

**已确认。** 准出设计分成三层，再由接受动作收口：

```text
Acceptance Criteria：什么叫完成
              ↓
Evidence：为判断完成而提供的材料
              ↓
Verification：依据这些材料得到的结论
              ↓
Acceptance：有权限的人决定是否准出
```

### 7.2 表达方式

以自然语言为主，配少量结构化信息，例如是否必选、如何验证、需要什么证据、由谁判断。不在第一版引入复杂规则语言，也不要求普通用户懂 JSON Schema 或编程测试框架。

建议每个条件都能回答“满足后会观察到什么”，避免只有“修好它”“做得更好”等无法对照的要求。

### 7.3 创建时确认，但不必永远禁止修改

用户明确要求在提出 Issue 时定义必要 Evidence。**尚未定案的是条件何时冻结以及中途如何变更。**

建议采用“有版本的确认”，而不是绝对禁止修改：Agent 可以提议调整，用户确认后形成新版条件，保留变更理由；对应验证需要重新判断是否适用。

不得为了把状态变绿，让 Agent 静默删除失败条件、降低阈值或改写已确认目标。

### 7.4 必选与参考条件

**建议草案。** 第一版可区分必选条件与参考信息。必选条件必须获得有效、足够的判断，才允许进入接受流程；参考证据用于帮助审阅，不必都变成机械闸门。

一条条件可以需要多份材料，一份材料也可以支持多条条件。不要为了表格整齐而强迫一对一。

### 7.5 验证计划不必都是可执行脚本

接口条件可以关联测试命令或请求用例；视觉条件可以关联截图、录屏和人类检查；文稿条件可能依赖交付文件、检查报告及人工判断。

第一版允许人工判定，只要清楚标记依据。不能自动化的要求仍然可以成为合法准出条件。

## 8. Evidence：证据模型

### 8.1 定义

**已确认：** Evidence 是针对某个准出条件，由工具、环境、系统、Agent 或人提供的可检查材料，并带有足够信息让审阅者判断其来源、适用状态和证明范围。

Evidence 不是一个没有上下文的附件，也不是 Agent 发出“已经测试通过”的一句话。

### 8.2 两条分类轴必须保留

用户最初提出按文件、图片、视频、接口输入输出等分类，并保留 `other` 扩展口；随后采纳按“证明什么”组织 Evidence 的建议。这两者不冲突，应分别保留。

| 分类轴   | 回答的问题               | 示例                                                                |
| -------- | ------------------------ | ------------------------------------------------------------------- |
| 证明语义 | 这份材料用于证明什么？   | 功能行为、视觉与交互、质量指标、数据正确性、内容完整性、约束符合性  |
| 材料载体 | 这份材料怎样展示和检查？ | 文本/日志、图片、视频、请求响应、测试报告、数据文件、文档、其他文件 |

语义大类用于审阅组织和验证指引；载体大类用于渲染、工具约定和结构化采集。

**不承诺把所有领域语义穷举完。** 第一版覆盖常见大类并保留扩展，内置类型的价值在于指导 Agent 生成更结构化、更易读的材料，而不是限制用户只能完成这些任务。

### 8.3 Evidence 的概念组成

以下是概念要求，不是强制数据库字段列表。

| 维度           | 需要说明的内容                                             |
| -------------- | ---------------------------------------------------------- |
| 对应条件       | 支持哪条或哪几条准出条件；具体想证明什么                   |
| 原始材料       | 截图、日志、请求响应、文件、报告等实际内容                 |
| 来源与生成方式 | 是工具采集、系统记录、Agent 组织、人工上传，还是其他来源   |
| 候选状态       | 材料针对哪个 Workspace 候选版本、哪些仓库与文件状态        |
| 环境           | 在哪台 Host、什么资源、什么应用或构建上生成                |
| 时间与过程     | 何时生成，触发了什么验证步骤，必要时保留参数及版本         |
| 判断关联       | 哪些 Verification 依据了这份证据；结论不能写回冒充原始事实 |
| 当前适用性     | 是否仍然适用，是否因候选、条件或环境改变而过期             |

实现时可用内部执行记录辅助定位，但对外仍以 Issue 为关联中心。

### 8.4 来源、可信度和生成方式不能混为一谈

Agent 可以提出验证步骤、调用工具、挑选材料并解释结果；工具或系统应尽量直接保存实际输出。人工也可以补充截图或判断。

**工程补充：** “由 test runner 生成”通常比“Agent 自称通过”更可检查，但并不天然证明测试覆盖正确。Agent 如果可以同时修改被测代码、测试与报告，就可能产生不充分甚至误导性的证明。

因此建议保留命令、退出码、原始报告和测试变更；重要基线检查由受保护的验证流程执行。来源完整、不可随意改写与可复现性比一个笼统的“高可信”标签更有价值。

### 8.5 原始证据不等于验证结论

```text
原始证据：登录失败后页面截图
判断：出现了预期错误文案，且用户仍停留在登录页

原始证据：API 请求、响应、状态码与测试输出
判断：非法输入被拒绝，且未产生不应有的写入

原始证据：PPT 文件及其页面预览
判断：所需章节完整、内容可读、没有明显排版遮挡
```

可以有多次判断，也可以由模型初审、人最终判断。后来的判断不应抹除先前原始材料。

### 8.6 状态绑定与过期

**已确认：** Evidence 必须绑定候选状态。候选内容改变后，之前证据默认失效，除非系统能证明相关验证不受影响。

**建议草案：** 第一版使用保守规则，不先做复杂影响分析。可先将“验证输入快照”固定下来，再执行检查。只记录 Git commit 不一定充分，因为 dirty/untracked 文件、测试配置和外部数据也可能改变实际输入。

过期原因包括：代码或交付文件变化、准出条件变化、合入前对齐主干、被测构建变化、关键环境或测试数据变化。单纯过了某个时间不一定失效；真正要说明的是依赖是否还成立。

**避免证据自我失效：** 截图、日志和报告本身是验证输出，不应因为保存这些输出就无限触发“候选又变了”。建议区分被验证的产品输入与受控 Evidence 输出目录；这种区分必须显式约定，不能用任意忽略目录绕过验证。

### 8.7 pass / fail / inconclusive / stale 的表达

对话已确认这些状态都需要表达。工程上建议把“判断”与“新鲜度”分成两个维度：判断可为 pass、fail、inconclusive；材料或判断又可能 fresh / stale。UI 仍可简化显示为“已过期”。

这样既保留“上次通过”的历史，也不会让过期的通过继续算作当前通过。该存储方式是建议，不替换已经确认的用户语义。

### 8.8 各场景如何落地

| 场景             | 准出条件示例                             | 原始 Evidence                                          | 判断方式示例            |
| ---------------- | ---------------------------------------- | ------------------------------------------------------ | ----------------------- |
| Web Server / API | 正确处理合法与非法输入                   | 输入、预期、响应、状态码、测试报告，必要时记录状态变化 | 确定性断言为主          |
| Web UI           | 指定页面流程可用、反馈正确、布局符合要求 | 截图、录屏、浏览器操作记录、相关日志                   | 断言 + 视觉检查 + 人审  |
| iOS / 移动 App   | 指定模拟器中的流程可完成                 | 构建身份、模拟器环境、截图、录屏、测试输出             | 自动化与人工结合        |
| 文稿 / 备课      | 覆盖指定内容、结构与使用要求             | 文档本身、预览、内容检查说明                           | 规则检查 + 人工内容判断 |
| PPT              | 所需页面完整且可读                       | PPT 本身、页面图、检查记录                             | 渲染检查 + 人工判断     |
| 数据处理         | 输出满足口径与一致性要求                 | 数据结果、输入口径、统计摘要、校验报告                 | 确定性校验 + 抽查       |
| 其他数字交付     | 满足用户声明的完成条件                   | 原文件及必要补充说明                                   | 人工判断兜底            |

这些只是复用模板，不是把所有工作都强制转换为软件测试。

### 8.9 材料保存与展示

**建议草案。** 需要考虑图片/视频预览、JSON 与文本易读展示、大文件限制、权限、保留周期及材料缺失后的状态。原文件不能只存在于已销毁的临时 worktree。

证据可以关联 Workspace 和 Issue 保存，不要求都并入产品 Git 历史；但接受记录所引用的材料必须在约定保留期内可访问，不能出现“当时似乎通过，但证据链接已失效”。

## 9. Verification 与 Acceptance：判断及准出

### 9.1 Verification 回答“条件是否成立”

验证可来自确定性检查、模型判断或人工判断。需要说明结论、依据、方法和适用状态。

没有测试过、不知道、环境无法启动、截图不足以判断，都不应标为 pass。它们可以是不确定、缺失或阻塞。

### 9.2 Acceptance 回答“是否允许改变 Workspace”

**已确认：** Acceptance 不等于“附件都上传了”，也不等于“Agent 认为自己做完”。它是有权限的人基于目标、候选变更、Evidence、Verification 和接受策略作出的决定。

### 9.3 第一版策略草案

建议采用：**全部必选条件都有有效通过判断 + 审阅者有接受权限 + 人明确接受 + 最终合入检查通过。**

模型给出 inconclusive 时，人可以直接检查原材料并留下人工判断；这是补充验证，不是把“不确定”暗中当作“通过”。

第一版不默认允许强制绕过必选失败条件。确有需要时，应走显式条件变更或另行设计有权限、理由和审计的豁免机制；是否提供豁免尚未决策。

### 9.4 Agent 自检与系统验证

Agent 在执行中可以自检、多次修复，这是高吞吐工作流的一部分。但最终系统必须清楚显示哪些材料是实际采集、哪些结论是模型解释、哪些检查由受保护流程执行。

产品应尽量降低人的重复劳动，而不是用更漂亮的“全绿”遮蔽不确定性。

### 9.5 Acceptance UI 草案

```text
Issue：目标与本次候选变更摘要

准出条件 A   通过        [查看 API 用例与原始响应]
准出条件 B   待人工判断  [查看截图与录屏]
准出条件 C   已过期      [查看过期原因 / 重新验证]

候选版本：……   验证环境：……   涉及仓库：……

[要求继续修改]  [接受并进入合入流程]  [放弃]
```

按钮名称不是最终 UI 文案。重点是让“材料不足”和“状态过期”直接可见，让用户知道接受的是哪一份候选结果。

## 10. Workspace、Git worktree 与多仓库

### 10.1 已选择的工作方式

**已确认及现状陈述：** Workspace 可以从一个目录开始；非 Git 目录初始化 Git；多仓库目录递归发现仓库；Issue 按涉及的仓库创建 worktree，再构造其执行 CWD；人工接受后将变更合回原 Workspace。

Git worktree 允许同一仓库拥有多个工作树，但部分仓库数据是共享的；它不是独立的安全沙盒。[S01]

### 10.2 文件并发与资源并发是两件事

worktree 解决候选文件相互覆盖的问题，不自动解决两个服务抢同一端口、多个 Agent 操作同一模拟器、共享浏览器登录态、写同一外部数据库或修改宿主机配置的问题。

因此隔离至少要分开考虑：候选文件、进程和网络、共享环境状态、外部副作用、凭证。资源池是补足这条链的后续核心方向，而不是 worktree 的附属 UI。

### 10.3 多仓库身份

**建议草案。** 用内部候选描述记录本次涉及的仓库、各自基线及候选版本；对用户仍展示为一个 Issue 的一次整体变更，不新增需要管理的“Workspace Revision 产品对象”。

这可以只是内部 manifest 或校验标识，用来绑定 Evidence 与合入预期。它是早期“workspace revision”建议的轻量化落实方式，不是已经决定建立复杂跨仓事务系统。

### 10.4 需要检查的仓库边界

建议在现有实现上补充验证：非 Git 目录初始化是否安全；Git worktree 的 `.git` 文件与普通 `.git` 目录是否都能识别；嵌套仓库、submodule、重复扫描和符号链接如何处理；仓库外文件由谁跟踪；已有 dirty 工作区如何保护。

仓库发现不应等于“无条件接管所有目录”。首次接入应能看清被纳入管理的范围、忽略策略和已有内容。

### 10.5 执行中扩大改动范围

**待决。** Issue 开始时选定部分仓库，执行中发现还需改另一个仓库怎么办？

建议显式扩展候选范围并刷新基线，不允许 Agent 直接跑到 canonical 目录修改未纳入隔离的仓库。已有证据需要重新检查是否仍然适用。

### 10.6 Git diff 与最终交付

文本 diff 是审阅入口，不是全部验收。二进制要有原文件或预览；生成型交付要声明哪些需要保留；`.gitignore` 中的临时文件不能因为留在磁盘上就被显示为已交付。

**待决：** 哪些大文件直接跟踪，哪些采用专门存储及版本引用；如何避免历史膨胀，同时保持 Workspace 可迁移、交付可恢复。

## 11. Merge Queue：串行合入与最新状态验证

### 11.1 已确认策略

**并发执行，串行集成。** 多个 Issue 可以同时工作；最终改变同一 Workspace 的步骤经一个 Workspace 级队列/锁串行处理。

这里的“全局”是相对于同一 Workspace，不是把所有用户、所有 Workspace 的接受操作锁在一起。若多个 Workspace 实际共用同一底层仓库或目录，锁域还需要进一步约束。

### 11.2 第一版保守流程

以下是对已确认决策的**实现草案**：

1. 人审阅当前候选变更及 Evidence，表达接受意愿。
2. Issue 进入该 Workspace 的 merge queue。
3. 获得锁，读取最新 canonical state，并检查候选、权限及目标条件是否仍有效。
4. 在候选工作树中对齐最新基线，例如执行 rebase；不能在 canonical 目录临时试合并后把未验证状态留在那里。
5. 出现冲突或需要实质代码修改时，暂停该项，交回继续处理，不直接沿用旧批准。
6. 对对齐后的候选运行关键验证并生成/关联新的 Evidence。
7. 确认待合入内容就是经过验证的内容；必要时重新请求人审阅。
8. 合入所有目标仓库，记录结果；完整成功后显示已接受/已集成。
9. 释放锁，随后按保留策略清理候选目录和资源。

第一版可以接受在锁内进行关键复验造成的等待。若验证耗时过长，后续再优化为候选预验证与短锁提交，并在锁内比较基线是否仍一致；不应先牺牲正确性追求短锁。

### 11.3 旧证据与旧批准的适用范围

**已确认：** 对齐新基线后不能盲用旧 Evidence。

**建议草案：** 把人批准的意图与批准过的候选内容关联起来。无冲突、无实质候选变更且规定复验全部通过时，可由明确策略允许继续；有冲突解决、额外修改、条件变化或新风险时，必须重新审阅。

是否对任何 rebase 都重新要求人点击，尚未决定。实现之前需要选定规则，不能让系统擅自扩大批准范围。

### 11.4 加锁不等于多仓库原子事务

**必须保留的工程边界：** Workspace 锁可以阻止平台自己的并发 merge 相互穿插，但不能自动解决“仓库 A 已合入、仓库 B 合入失败、进程崩溃”的部分完成问题，也不能阻止不遵守该锁的外部写入或读取。

**建议的最小恢复方案：** 所有仓库先准备和验证，持久化记录基线与预期结果，再逐个提交集成结果；若发生部分完成，停止后续队列、保留事故状态和恢复信息，不把 Issue 标成完整成功。恢复应检查实际仓库状态，优先完成或安全修复，不能无条件 `reset --hard` 覆盖外部变化。

将多个仓库准备好后通过快照指针统一发布，可以作为远期方向；这不是第一版必选项，也不能在未实现前声称原子可见性。

### 11.5 锁与外部写入

建议第一版明确 canonical 目录的写入约束。用户本机手动修改、其他程序写入，或共享仓库被另一 Workspace 修改，都可能绕过平台队列。

检测到目标分支或关键文件变化，应停止并重新对齐，不能带着过期前提继续发布。分布式部署时，锁需有持有者身份、失效与恢复规则；租约过期不能让旧持有者继续写入。

### 11.6 接受范围不包含所有外部副作用

合入文件可以受 Git 控制，但部署、发消息、修改外部数据库等动作不因用户之后放弃 Issue 而自动回滚。

**建议草案：** 第一版把候选执行限定在开发/测试环境，需影响真实外部系统的动作另行申请权限。不要把最终 accept 当作此前所有外部动作的追认。

## 12. Tools、Browser Use 与 Computer Use

### 12.1 对实现顺序的关键修正

最初设想是“先完成 Evidence / Acceptance，再接工具”。讨论后确认：Evidence 的真实构造本身就依赖工具及可观测环境。

因此不是先做一个空证据框架，也不是等完整资源平台落地。**应先定义最小 Evidence 契约，接入能产出真实证据的工具和至少一种必要验证环境，一起打通闭环。**

**后续讨论明确的命名与边界：** Roadmap 中的“基础 Tool Use”指工具接入、实际操作与证据采集，先从本地做起；“共享资源调度”指多个 Issue 对工具背后环境的分配、独占、排队、释放与故障回收。Browser、Computer Use、Simulator 的操作能力按验证场景随 Tool Use 接入，是相应 Evidence / Verify 的前置，不因为共享资源调度排在后面而推迟。首次接入即应提供必要的环境身份、授权、隔离、占用保护与清理；后续再统一资源抽象与调度。

### 12.2 两类工具能力

| 类别                   | 例子                                                | 最小集成重点                                       |
| ---------------------- | --------------------------------------------------- | -------------------------------------------------- |
| 易产生结构化结果的工具 | Shell、test runner、HTTP client、文件检查、数据校验 | 实际输入、输出、错误、退出状态、原始报告与候选关联 |
| 交互环境及其控制工具   | 浏览器、桌面、iOS Simulator、真机                   | 环境实例、控制通道、占用权、隔离、截图/录屏及清理  |

“确定性工具”在本文中指容易用明确操作和断言检查的能力，不意味着任何 Shell 命令都无副作用，或任何测试结果都不受环境波动影响。

### 12.3 Browser Use：控制层与展示层分离

用户最初提出在 Web UI 旁边打开 iframe，并操作 DOM。已确认的修正是：**普通父页面不能直接读取和操作任意跨域 iframe 的 DOM；同源策略限制这种访问。** 不能把任意网页自动化建立在此假设上。[S02]

建议结构：

```text
Agent
  ↓ 工具调用
Browser Provider / Adapter
  ↓ 自动化控制通道
受管理的浏览器实例或隔离会话
  ├── 执行页面操作
  ├── 采集截图、日志、可用的操作记录
  └── 向 Web UI 提供预览或远程会话入口
```

Web 侧可以展示自己控制的预览页面、截图或远程浏览器会话；这与“通过 iframe 父页面操控目标站点”不是同一实现。

Playwright、其 MCP 接口或 CLI 可作为调研候选。官方 Playwright MCP 项目同时提示编码 Agent 场景可以考虑 CLI + Skills，因此不应把 MCP 当成唯一接入方式。[S03]

**待决：** 采用哪一种 Browser Provider、怎样在 Web 中展示实时会话、是否允许用户接管、怎样恢复 Agent 控制。接管时需避免人与 Agent 同时点击同一个环境。

### 12.4 Computer Use：能力不等于现成部署包

用户希望复用 Claude 的 Computer Use。方向保留，但“直接用 Claude 的那个 MCP”需要纠正：当前官方 computer use 是应用侧执行的工具能力，需要接入方提供计算机环境与动作执行；它本身不等于一个自动完成部署、鉴权和隔离的通用 MCP Server。[S04]

可以用适配器包装现成实现，并按需要通过 MCP 暴露。是否已有足够成熟、符合许可和部署需求的实现，要作为选型任务验证，不能写成已完成接入。

**建议：** 不把完整 Computer Use 作为所有首发场景的前置要求。API/文档场景可先用结构化工具，Web 端到端场景先接浏览器；确需桌面交互时再加入 Computer Resource。

### 12.5 iOS Simulator 与移动端

这是用户正在构建 iOS App 时提出的真实需求：Issue 可能都需要同一台或同一组 Simulator 验证，因此它既是工具背后的环境，也是可竞争资源。

需要将目标平台、运行时、设备配置、应用构建、安装/重置步骤和截图录屏关联起来。实际支持范围必须在选定宿主机与工具链上验证，不承诺任意宿主机都可构建或运行任意目标平台。

### 12.6 最小工具层的契约建议

内部至少统一：声明能力、检查权限、指向实际执行环境、触发动作、接收结果/错误、登记 Evidence、支持超时与清理。

不要求所有工具都遵守一种自创外部协议。已有 SDK、CLI、HTTP、MCP 都可以通过适配器进入同一证据与权限链。

## 13. Resource Pool：资源与调度

### 13.1 为什么资源池是独立方向

**方向已定。** 多 Issue 并发后，稀缺的不是只有 CPU。端口、浏览器上下文、桌面会话、模拟器、真机、GPU 或某类宿主机，都可能被多个 Issue 或多个 Workspace 争用。

产品因此需要的不只是创建 sandbox，而是知道资源在哪里、谁有权使用、谁正在使用、何时可释放、异常后怎样恢复的调度层。

这一方向在当前 Roadmap 中称为**共享资源调度**。工具层负责“操作浏览器并截图”等实际动作和证据采集；本层负责“把哪个浏览器实例分配给谁、其他任务如何等待、用完或出错怎样回收”。先统一单机已有环境的管理，再扩展跨宿主机资源；工具接入所需的最小隔离与清理从首次使用就具备。

### 13.2 能力类型与实际实例分开

**建议草案：** Issue 需要的是某种能力，例如“可运行目标 App 的 Simulator”；调度器分配的是具体实例，例如“Host B 上已准备好的设备实例”。

用户不必管理内部租约，但应能理解“正在等待模拟器”“环境离线”或“需要选择可访问的宿主机”。

### 13.3 初始资源分类

| 类型         | 例子                                   | 注意事项                                    |
| ------------ | -------------------------------------- | ------------------------------------------- |
| 独占交互资源 | 一个桌面会话、一个正在被操作的设备实例 | 同时控制会破坏验证过程                      |
| 可切分容量   | CPU、内存、部分 GPU 配额               | 先做简单容量限制，不急于复杂调度算法        |
| 可隔离会话   | 浏览器 Context、测试环境实例           | 可能共享底层进程，但状态与占用权应分离      |
| 地址资源     | Host 上的端口、可访问的服务端点        | 标识需要包含宿主机/网络环境，不能只有端口号 |
| 外部受限能力 | 有速率、额度或权限限制的 API           | 不完全等同于硬件池，还需要配额及副作用策略  |

以上分类是建模建议，并非要求五套独立模块。

### 13.4 最小资源生命周期

```text
注册 / 发现 → 健康检查 → 可用
                     ↓ 申请与授权
                  分配占用权
                     ↓
                  使用 / 心跳
                     ↓
              释放 → 清理 → 再次可用

异常：离线 / 超时 / 污染 / 清理失败 → 隔离或待恢复
```

调度层应知道当前持有者、资源用途、超时边界及清理状态。不能因租约到期就假定旧 Agent 已停止控制，导致同一资源分给两个仍在活动的持有者。

### 13.5 资源竞争与公平性

第一版可以采用简单队列和显式独占；共享型资源先限制并发数量即可。后续再考虑优先级、跨 Workspace 公平性、配额、亲和性和多资源协同分配。

Agent 被阻塞等待用户时，哪些资源保留、哪些释放，需要按资源重建成本决定；不能默认每个 Issue 从开始到结束一直占住模拟器。

### 13.6 从单机到多机

建议先在单 Daemon 上把端口与一种浏览器/模拟器资源管理正确，再扩展成多个 Daemon 注册资源。多机不是简单把资源列表拼起来，还涉及连通性、鉴权、环境版本、租约恢复和可信 Evidence 来源。

完整分布式调度不应阻塞最小证据闭环，但第一个 Browser/Simulator Adapter 就应有资源身份、独占与清理意识。

## 14. Build Here, Verify There：跨环境构建与验证

### 14.1 已确定的方向

构建与验证可以分布在不同宿主机。最终用户关心的是可靠结果和可检查证据，不需要所有步骤共用一个物理目录或一个操作系统。

同时，不能把这一方向理解成“只要收到一个 pass 就够了”。必须知道远端验证的究竟是哪一份内容。

### 14.2 最小跨环境链路草案

```text
Issue 的候选输入快照
        ↓
在适合的 Host 上构建
        ↓
产生带身份的构建输出 / 发布到测试环境
        ↓
匹配并申请验证资源
        ↓
在目标环境安装、启动或连接被测内容
        ↓
执行检查，采集原始 Evidence
        ↓
将结果、环境与被测内容身份关联回同一 Issue
```

构建输出可以用文件或受版本管理的引用表示，不需要因此恢复被否定的独立 Asset 产品对象。

### 14.3 必须一致的身份链

建议能追溯：准出条件版本 → 候选输入 → 构建内容 → 验证环境 → 原始 Evidence → 判断 → 最终合入内容。

不能用旧 App 的截图证明新代码，也不能把远端另一份分支测试报告挂到当前候选上。Web 热更新、部署缓存或重复端口也可能造成“测试的不是预期版本”，需要在场景验收中覆盖。

### 14.4 环境兼容与限制

构建工具链、目标平台、架构、依赖、测试数据和资源能力应匹配。某些任务可以传构建包，某些任务需要在验证 Host 重新准备源码和环境，某些任务只需提供可访问的服务端点。

采用哪条传输路径属于场景实现，而不是一开始要求统一远程文件系统。

### 14.5 安全与副作用

跨机材料传输要鉴权，证据与日志要避免泄露秘密；资源不可用应变成可解释的等待或阻塞。重复交付、网络中断和重试不能导致未经授权的重复外部操作。

## 15. 多 Harness 接入与执行层边界

### 15.1 现有选择

**已确认。** 通过 SDK 等正式接入点复用 Codex、Claude Code 等 Harness，保留其上下文管理、工具调用、subagent 和执行恢复能力，而不是先复刻一套 Agent loop。

当前官方资料也区分不同集成入口：Codex SDK 面向程序化任务，App Server 面向包含认证、会话历史、审批和流式事件的深度客户端集成；Claude Agent SDK 提供 Claude Code 的工具、循环和上下文管理能力。[S05][S06][S07]

这支持“优先集成”的方向，但不能据此断言现有适配代码已经选对全部接口。可在不重写产品核心的前提下审查现有接入方式。

### 15.2 应当统一什么

**建议草案。** 统一用户语义和业务边界：启动/继续同一 Issue、用户输入、阻塞、权限请求、状态事件、工具结果、Evidence 登记、候选目录和停止控制。

不同 Harness 的独有能力可通过能力声明保留，不能为了一个整齐接口把所有实现削减为最低共同能力，也不能把某一家 session 格式直接变成产品领域模型。

### 15.3 不要混淆 Model Provider 与 Harness

用户未来填写 Provider 信息，解决的是模型或服务接入的一部分；它不会自动提供工作目录、恢复语义、工具实现、证据采集和资源调度。

一个 Harness 可以接不同 Provider，不同 Harness 的配置、认证、状态恢复方式也可能不同。云端路线需要明确运行的是哪种 Harness，而不是只增加一个 API Key 表单。

### 15.4 本产品负责什么

建议稳定持有：Workspace 的可信状态、Issue 意图、准出条件、Evidence 及判断、接受权限、合入保护、资源协调与跨环境追溯。

尽可能把模型内循环、上下文压缩和厂商特有执行行为留给现成 Harness。但持久业务记录不能只寄存在一个会话上下文里，否则更换或崩溃后无法继续。

### 15.5 版本、认证与分发核对

SDK、插件格式和宿主环境可能变化，因此应记录经验证的兼容组合，而非默认所有新版自动兼容。

**对外发布前核对：** Claude Agent SDK 当前官方文档对第三方提供 claude.ai 登录/额度及产品品牌展示有明确约束，不能把“本地能跑通”视为产品分发授权。具体接入应按官方许可、认证与品牌要求核对。[S07]

同样需要核对所使用的 UI、图标、代码、SDK 和依赖的实际来源及许可。此项是发布检查，不是对现有实现作侵权或合规结论。

## 16. DeepSeek Harness、Plugins、MCP、Skills 与 Hooks

### 16.1 产品识别与核查

口述中出现的 “Tip six harness / plugins” 在后续对话被识别为 **DeepSeek Harness**。本次整理确认：DeepSeek 官方公开仓库确有这一项目，其定位采用 “Everything is a Plugin”，底层使用 Cordis。[S08]

这次核查支持产品名称与基本架构，不代表此前口头回答已经做过源码审计。

### 16.2 它不是只有一层 MCP 调用

官方开发文档说明，插件可以是导出加载入口的 TypeScript 模块；通过 `apply(ctx)` 获得运行时上下文、注册能力，并通过 `inject` 声明服务依赖。文档也描述了随插件卸载清理注册项及显式资源清理的机制。[S09]

服务是插件提供给其他插件的命名能力，例如工具服务或模型服务；插件既可以消费服务，也可以提供服务。[S10]

因此它不只是“核心程序调用外部 MCP Server”，而是具有内部扩展契约、依赖关系与生命周期的运行时组合机制。对外工具协议与内部插件机制可以叠加。

### 16.3 “三层”应怎样准确表达

本次读取的官方架构文档使用了三个角色来描述可替换能力的边界：**Service Definition、Service Provider、Consumer**；它们可以由同一包组合，也可以在需要时拆开。[S11]

可以将其理解为“能力接口—能力实现—能力使用方”。不要未经说明就把它改说成官方固定的“MCP—Skills—Hooks 三层”，也不要假定用户最初口述必然精确指这三个角色。

### 16.4 与 MCP 的关系

MCP 是 AI 应用连接外部工具、数据等能力的协议；它并不负责替本产品定义 Issue 生命周期、接受策略、插件生命周期或全部权限逻辑。[S12]

还要避免名称混淆：MCP 的 `resources` 用于向客户端提供可读取的上下文数据，**不等于本文需要调度、租用与释放的机器/模拟器资源池。** 二者可以由适配器连接，但语义不同。[S13]

### 16.5 Skills、Hooks、Plugins 分别解决什么

| 机制    | 主要作用                           | 对本产品的参考                       |
| ------- | ---------------------------------- | ------------------------------------ |
| MCP     | 连接外部工具及上下文能力           | 复用工具生态，不必为每个系统自创协议 |
| Skills  | 打包工作指导与可复用资源           | 把经验证的方法沉淀回 Workspace       |
| Hooks   | 在生命周期节点触发处理或检查       | 接入结果采集、通知、辅助控制等动作   |
| Plugins | 打包或替换扩展能力；含义取决于宿主 | 不应假定所有厂商插件格式相同         |

Agent Skills 有公开的 `SKILL.md` 格式规范；Claude Code 的插件文档将插件描述为可包含 skills、agents、hooks、MCP 等组件的组合，Hooks 文档则定义了生命周期触发机制。[S14][S15][S16]

**结论：** 借用已有格式并逐项适配，比自创一个号称覆盖所有 Harness 的万能插件标准更稳妥；但“兼容其中一项”不等于整套配置都能无损互通。

### 16.6 本产品的插件边界建议

**建议草案，未批准采用具体框架。**

```text
稳定的产品语义
Workspace / Issue / Criteria / Evidence / Verification / Acceptance
                         ↓ 扩展契约
可替换的实现
Harness Adapter / Tool Provider / Resource Provider /
Verifier / Evidence Renderer / IM Adapter / Storage Adapter
```

“核心语义稳定”不意味着其存储实现永远不可替换。可以插件化数据库或文件存储 Provider，但不能让插件随意取消人工接受、绕过权限或使旧证据重新变成有效。

### 16.7 值得借鉴的技术点

建议研究能力接口与 Provider 分离、显式依赖、资源清理、版本化能力声明，以及可追溯事件。浏览器、模拟器和远程 Host 都可从同样的接口纪律受益。

不建议为了实现插件化而重写已有可用的 Chat 和 Harness 接入，也不建议第一版就建设插件市场、完整热更新系统或不可信插件沙盒。

### 16.8 插件不是安全边界

进程内插件能扩展核心，也意味着可能具有较高宿主权限。MCP 也不是天然无风险通道。

**建议：** 开源早期明确只支持可信插件，记录所需权限与版本；插件不能通过提供一份“pass”结果就自行完成 accept。第三方代码隔离和供应链审计应另立工作项，不能用“插件化了”替代安全设计。

## 17. Workspace 的能力积累与自我演进

### 17.1 产品内容和工作能力一起增长

用户接受的核心思路是：Issue 可能交付一个功能，也可能顺带产生测试脚本、部署 checklist、项目约定或可复用 skill。下一次工作可以利用这些内容，而不必从零重新解释。

这就是 Workspace 的“自我增强”：增强的是可访问的上下文、工具和经过验证的方法。

### 17.2 可沉淀内容示例

代码与文档之外，还可包括测试、验证脚本、构建说明、常见错误排查、AGENTS.md / Harness 对应的项目指令文件、Skills、工具配置及流程模板。

是否自动识别、建议或分类这些内容，尚未定案。不需要因此创建独立 Capability Asset 生命周期。

### 17.3 防止无序积累

**建议草案。** 不把每次对话、临时日志和偶然成功的方法全部变成永久指令。沉淀内容应有适用条件、可验证价值及与现有规则的一致性。

“上下文更完整”应理解为相关、可检索和可使用，而不是把全部历史塞入每一轮模型请求。具体检索、索引与知识维护方案可后置。

### 17.4 自我演进也必须经过闸门

修改执行脚本、准出检查、项目指令或权限配置，有时比修改一般业务文件影响更大。

建议至少在审阅中突出此类变更；重要验证基线不能由正在被验收的候选自由削弱。需要更高权限或额外审阅的文件范围，属于后续权限设计。

## 18. IM 接入与多入口交互

### 18.1 已提出的体验

后续讨论明确：**IM 接入与账号、权限体系是独立能力。** IM 是额外交互入口，个人也可以使用；Foundry 的账号、登录、团队成员和操作权限单独建设。两者通过 IM 身份到 Foundry 账号的绑定衔接，所有入口沿用该账号的授权判断。IM 操作依赖可用的身份映射与权限契约，不要求完整团队管理先完成。

**当前接入范围：** 先建立通用 Bot Adapter，统一入站事件、出站动作、身份和消息关联，优先评估业界通用 Bot 协议的复用；具体协议尚未选定。MVP 只接 Lark，打通任务发起、进度通知、人工回应与 Foundry 账号映射。早期讨论中的 Slack / Telegram 保留为后续适配方向，不属于 MVP。

这是增加一个 UI，不是给每个入口创建一个独立 Workspace 或另一套 Issue 真相。

### 18.2 建议保留的统一语义

Web 与 IM 都应回到同一 Issue、同一准出条件、同一 Evidence 和同一接受权限。无论从哪里恢复工作，都不要求用户选择内部 Run。

IM 适合轻量沟通、通知与发起；复杂 diff、证据比较和高风险审阅可以先跳回 Web。

### 18.3 平台差异

“group—Workspace、thread—Issue”是概念映射，不承诺所有 IM 具有一致的线程模型。先验证 Lark 的会话、消息关联、交互、文件、鉴权与重复事件处理，由 Adapter 转成通用契约；保留平台能力差异。后续适配其他 IM 时复用核心任务逻辑。

Linear 已有 Slack 与 Issue 的同步 thread，可作为入口交互参考，而不是本产品已经实现的能力。[S21]

### 18.4 接受权限不能被聊天入口稀释

一个人能在群里发消息，不意味着他有权接受变更。建议第一版由 IM 提供审阅入口，在 Web 中执行正式 accept；如果未来在 IM 里接受，仍需可靠身份映射、权限检查与明确候选绑定。

## 19. 云端 Workspace 与文件系统

### 19.1 当前与目标

当前 Agent 和 Workspace 都跟随 Daemon，位于用户的执行宿主机侧。

**当前范围澄清：** 托管的是 Workspace 本身，包括项目文件、内容与持久状态，让本地或远程执行端按权限访问同一个逻辑文件系统。早期“填写 Provider 信息即可在服务端运行 Agent”的执行托管设想不属于本项要求，也不是云端 Workspace 的前置。

### 19.2 渐进路线

| 阶段   | 方式                                            | 解决的问题                               |
| ------ | ----------------------------------------------- | ---------------------------------------- |
| 当前   | 用户宿主机 Daemon 持有 Workspace 并执行         | 利用用户已有环境与工具                   |
| 接入   | 定义云端 Workspace 身份、文件访问与候选版本契约 | 让授权执行端取得正确内容并提交候选变更   |
| 持久化 | 托管项目文件与持久状态，和执行端解耦            | 执行端断开或更换，不丢失已接受的项目状态 |
| 增强   | 按实际需求优化存储、索引及语义访问              | 在稳定文件与版本语义上改善效率           |

同一逻辑文件系统不预设物理存储方案；挂载、文件接口或候选快照需通过实际读写、构建、验证与接受场景核对。执行端仍由现有 Daemon 模型承接，不要求平台供应执行机器。

### 19.3 用户提出的接口方向

讨论曾涉及类似本地文件系统的 read / write / seek、文件操作工具接口、可能的 MCP、LSP 相关能力及语义搜索。

**保留为探索方向，不做技术定案。** 最低目标是远端内容可被授权执行端可靠读取和修改；高层索引与语义工具是增强能力，不应替代对实际执行所需文件语义的验证。

### 19.4 远程文件 API 不自动等价于远程开发环境

**工程推论。** 即使 Agent 能读写云端文件，Shell、构建、测试或语言工具仍需在明确的执行环境中使用相匹配的文件状态。因此文件访问、进程执行、路径、依赖和候选版本必须一起考虑。

可以选择远程挂载，也可以物化候选快照、使用执行节点本地目录或按构建产物传输；应通过真实场景验证后选择，而不是先造通用文件系统。

### 19.5 后置理由

云端 Workspace 是有价值的长期方向，但短期的证据闭环尚可在 Daemon 模式下完成。先用真实任务验证价值，再决定存储一致性、缓存、同步、锁语义、大文件及备份范围，可减少与当前产品主线无关的基础设施投入。

远端化不改变 canonical 语义：仍只有经过接受的产品状态进入 Workspace，不应演变成多个节点随意写共享目录。

## 20. 权限、信任边界与治理

### 20.1 已确认的关键权限

Workspace 是产品最重要的资产，accept 会改变它；因此团队成员不能天然都拥有接受权。

**建议草案。** 权限至少分开考虑：查看、创建与沟通、控制执行、使用资源与凭证、确认准出条件、接受、放弃、管理 Workspace。具体角色及继承方式未定。

### 20.2 不能把基础安全全部放到“团队版以后”

完整 RBAC 可以后置，但远程 Web 控制宿主机、Agent 执行命令和接受变更，从单用户版本起就需要明确边界。

开源早期建议限定可信单用户场景，同时具备 Daemon 配对/鉴权、授权目录范围、基本工具权限、敏感凭证保护、明确的 accept 身份和必要审计。

### 20.3 控制面与执行面的信任

建议不要把产品 Server 的管理凭证直接暴露给 Agent 可执行的代码。工具、网页、仓库内容和模型输出都不应能自行提升为控制面指令。

Anthropic Managed Agents 的工程文章将 Harness、执行环境与持久会话拆分，并强调把敏感授权与不可信执行环境隔离；这是可参考的设计原则，而非要求使用它的服务。[S22]

### 20.4 证据安全与隐私

截图可能包含账号信息，日志可能包含 token，请求响应可能包含用户数据。证据应与 Issue / Workspace 权限一致，并有必要脱敏与保留策略。

上传的 HTML、SVG 或其他主动内容也不应在主站权限上下文里不加区分地执行。证据渲染与工具执行都需要自己的边界。

### 20.5 关键变更的审计

建议保留：谁创建及修改准出条件、谁触发/恢复工作、谁授权资源、谁给出人工判断、谁接受/放弃、接受针对的候选是什么、最终合入结果是什么。

审计记录不能仅依赖可被普通 Agent 改写的聊天摘要；物理存储实现仍待选定。

### 21.4 更有价值的差异化假设

**建议聚焦一个可验证的组合，而不是单项功能独有性：**

> 使用用户选择的 Harness 与执行资源，让多个 Issue 在同一逻辑 Workspace 上并发工作；每个交付都能提供绑定实际候选状态的证据，经人审阅与安全集成后，成为 Workspace 的新可信状态。

其中可能形成价值的组合包括：持久 Workspace、跨 Harness 的一致用户语义、异构本地/远程验证资源、证据到候选再到合入的完整链条，以及开源可部署性。

资源池尤其值得验证，但不能未经调研就断言其他产品没有相似能力。需要用“用户完成一个具体任务是否更省力、更可靠”来验证，而不是依赖概念独特性。

### 21.5 用户分层假设

| 阶段 | 候选用户                                                        | 需要先证明的价值                          |
| ---- | --------------------------------------------------------------- | ----------------------------------------- |
| 早期 | 同时使用多个 Agent、会提出多个并行 Issue 的独立开发者和重度用户 | 不必管理多个会话与目录；审阅和恢复更顺畅  |
| 中期 | 小型产品/工程团队，尤其有多仓库或特殊验证环境                   | 共享上下文、资源竞争、接受权限与集成可控  |
| 后期 | 文稿、教育、PPT、数据等非纯工程数字工作                         | 不懂 Git 也能提出目标、查看材料、接受结果 |

这是当时建议的切入顺序，不是已验证的客户群画像。第一批真实任务可优先来自创始人自己的工作流，包括正在构建的 iOS App。

### 21.6 产品定位建议

对外不必立即使用“Agent OS”“元 Harness”等术语。可先描述为：**一个以 Workspace 为核心、支持多 Agent 并发执行和可验证交付的工作平台。**

主张应落在体验结果：提出 Issue 后能持续推进；中断后可继续；审阅时不翻长聊天找证据；接受后 Workspace 确实进入经过验证的新状态。

### 21.7 产品验证方式

建议用同一组真实任务比较当前工作方式与本产品：多 Issue 并发、一次掉线恢复、一次主干前移、一次需要 Simulator 的验证、一次非代码文档交付。

观察人工介入次数、审阅耗时、等待原因、错误证据比例和真正接受的交付数量，不把 token 消耗或 Agent 同时运行数当成全部成绩。

## 22. 分阶段 Roadmap

### 22.1 排序原则

**已确认的优先方向：** 先把 Evidence / Acceptance 闭环做到可开源；工具层是闭环依赖，不能全部后置。

下列里程碑与任务拆分是**建议草案**。阶段代表依赖和风险，不是承诺日程。部分工作可以并行，完整团队功能不必等云端文件系统，基础权限也不能等团队版。

### 22.2 总览

后续 Roadmap 编排将 M2 的单机调度与 M3 的跨 Host 扩展合并为“共享资源调度”一项，异地验证作为其中的应用场景。下表保留两个实施阶段，用于区分单机管理与跨机授权、构建传输、版本关联和恢复等工作，不再对应两个独立的 README 条目。

| 阶段                   | 目标                                              | 范围                                                                                | 退出标准                                                       |
| ---------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| M0：现有能力基线       | 明确哪些已经可用、哪些只是已有 UI 或代码          | Chat、Harness Adapter、Daemon、worktree、多仓库、接受逻辑                           | 用演示/测试确认现状，记录差距，不盲目重写                      |
| M1：可开源最小闭环     | 从明确完成标准到可信接受与合入                    | Criteria、最小工具与 Evidence、Verification、人审、恢复、merge queue、基础安全      | 代表任务端到端完成，错误/过期/冲突不会被误报成功               |
| M2：共享资源调度       | 统一管理多个 Issue 的环境分配与竞争，先从单机做起 | 在已接入的浏览器、桌面、Simulator、端口等资源上管理分配、独占、排队、释放与故障回收 | 两个 Issue 争用资源时可等待、释放、复用，不串台                |
| M3：多 Host 与异地验证 | 打通 build here, verify there                     | 多 Daemon、资源授权、材料/构建传输、环境身份与恢复                                  | 构建与验证分离仍能追溯到正确候选，掉线不重复误操作             |
| M4：账号权限与 IM 接入 | 分别建设身份授权体系和额外交互入口                | Foundry 账号、团队成员与操作权限；通用 Bot Adapter，MVP 接 Lark                     | 不同入口保持一个 Issue，IM 身份映射到 Foundry 账号并沿用其权限 |
| M5：云端 Workspace     | 托管项目文件与持久状态                            | 统一逻辑文件系统、授权访问、候选版本与恢复                                          | 执行端可更换，已接受状态不丢失，读写与合入对应正确版本         |
| M6：高级存储与生态     | 根据真实瓶颈扩展                                  | 存储优化、高级索引、插件生态、调度优化；基础远程文件访问归入 M5                     | 有已验证需求，且不破坏 Workspace / Issue / Acceptance 语义     |

后续讨论已将“Workspace 能力积累”和“高级存储与扩展生态”移出当前 Roadmap：前者是 Issue 闭环带来的效果；自动技能提炼及 M6 的宽泛扩展保留为未排期探索，出现具体需求后再定义功能，不作为接手实施任务。

M1 按首发场景接入所需工具及验证环境，并具备环境身份、授权、隔离、占用保护与清理；M2 在这些基础上统一共享资源调度。M4 的基础鉴权与接受权限也应在 M1 具备，不能后置到团队版。

### 22.3 M1 推荐首发范围

以可信单用户、已有 Daemon 部署方式为起点，保持当前已支持 Harness 的基本体验；完成一条结构化工具证据链。若首发演示包含 Web UI 功能，加入一个可复现的浏览器验证路径，而不是只上传手工截图充数。

证据的初始内置载体可覆盖文本/日志、结构化测试或请求响应、图片、普通文件，并对视频/其他文件保留通道。是否首发录屏取决于选定场景，不必为了类型齐全实现所有采集器。

**首发不要求：** 完整分布式调度、任意电脑远程控制、所有模拟器与真机支持、复杂多租户、通用云文件系统、插件市场、自动接受、智能影响分析或严格跨仓原子发布。

### 22.4 M1 开源前验收清单

- [ ] 能创建 Issue，确认其目标和必选准出条件。
- [ ] Agent 在隔离候选环境中工作，不直接污染 canonical Workspace。
- [ ] 至少一种实际工具生成原始 Evidence，而非只保存 Agent 的结论。
- [ ] Evidence、验证结论、候选状态和准出条件能关联。
- [ ] 失败、不确定、缺失和过期均不会被误当作有效通过。
- [ ] 用户可审阅材料、要求继续、接受或放弃；不会被迫管理 Run。
- [ ] 中断后能继续同一 Issue，阻塞原因与下一步可理解。
- [ ] 两个 Issue 并发工作，合入通过队列串行保护。
- [ ] 排队期间主干前移会触发对齐与规定复验。
- [ ] 多仓库部分合入能被检测并停止后续操作；未支持的保证明确声明。
- [ ] Evidence 不随临时候选清理而意外丢失；主站展示与访问权限合理。
- [ ] Daemon 鉴权、凭证范围、工具权限和人工接受身份具备基本保护。
- [ ] 安装、配置、支持范围、许可证/依赖核对及一个端到端示例可供开源用户使用。

开源不等于“生产安全、任意场景可用”。允许首发声明为有限范围的开发者预览，但不可将已知数据丢失或越权路径包装成成熟能力。

### 22.5 主要依赖

```text
当前实现核对
    ├── 准出条件确认
    ├── 候选状态与 worktree 边界
    └── Daemon / 工具基础权限
                 ↓
最小工具执行 + 原始 Evidence 采集
                 ↓
验证判断 + 过期处理
                 ↓
人工审阅与接受
                 ↓
merge queue + 最新状态对齐 + 复验 + 恢复
                 ↓
端到端演示与开源准备

场景所需工具与验证环境 → Evidence / Verify
已接入环境的身份、占用与清理 → 共享资源调度（先单机）→ 多机调度 / 异地验证
统一 Issue / 权限模型 → IM 接入 / 团队协作
Workspace 文件与版本契约、权限 → 持久云端 Workspace → 授权执行端访问
```

## 23. 可直接拆分的近期执行任务

所有任务状态均为 **待核对 / 待实施**，不是已经创建的项目 Issue。可按现有仓库结构分配负责人，不预设技术语言或模块名。

### T-01｜核对现有实现与适配能力

**阶段：M0。依赖：无。关联：D-01～D-04、D-19。**

目标：沿用户描述的当前路径实际跑一次，列出现有 Chat、两类 Harness 接入、Daemon、单仓/多仓 worktree、接受逻辑的能力边界。

交付：现状与差距清单、支持的接入版本、一个可重复演示流程。验收：每项“已实现”都有可观察依据，未知项不标完成；不因本文而先做大规模重构。

### T-02｜实现准出条件的创建、确认与变更

**阶段：M1。依赖：T-01。关联：D-09、D-14。**

目标：自然语言 Issue 可形成可编辑条件清单，人确认后进入执行。

交付：条件展示、必选标识、验证方式提示及变更记录。验收：Agent 不能静默删除或降低已确认条件；修改条件后能识别受影响的判断。无需实现复杂 DSL。

### T-03｜建立候选状态身份与改动边界

**阶段：M1。依赖：T-01。关联：D-01、D-03、D-04、D-12。**

目标：准确说明每个 Issue 正在修改什么、准备验证什么。

交付：单/多仓基线、候选输入身份、被跟踪文件与生成材料边界。验收：dirty/untracked、二进制和仓库外文件按明确策略处理；Evidence 能区分不同候选；对外不增加 Run 或 Asset 管理流程。

### T-04｜接通结构化工具证据链

**阶段：M1。依赖：T-02、T-03、T-11 的基础权限部分。关联：D-10～D-12、D-17。**

目标：先用现有 Shell / test runner / HTTP 能力产生真实可检查材料。

交付：工具输入/结果采集、报告与日志保存、条件及候选关联。验收：成功、失败、超时都保留真实结果；不能把 Agent 的自然语言摘要当作工具原始输出。无需先完成通用插件系统。

### T-05｜接入最小 Browser Resource

**阶段：M1 或 M2；首发承诺 Web 端到端验证时进入 M1。依赖：T-03、T-04 的登记契约、T-11。关联：D-17、D-18、D-20。**

范围归属：基础 Tool Use。本任务接入 Browser 操作、证据采集与必要环境管理；其所在阶段由 Web 验证承诺决定，不等待统一共享资源调度。

目标：在独立受控浏览器环境中打开本 Issue 的应用，操作并采集截图等材料。

交付：一个选定 Browser Provider、必要端口/端点管理、会话身份与清理。验收：不依赖任意跨域 iframe DOM；两个 Issue 不共享错误页面或登录态；证据属于正确构建和环境。

### T-06｜分离 Evidence 与 Verification，并实现过期

**阶段：M1。依赖：T-02～T-04。关联：D-10～D-15。**

目标：原始材料、判断和当前适用性各有明确语义。

交付：pass / fail / inconclusive / stale 的展示与判定，最小人工判断入口。验收：改动候选或条件后，旧通过不能继续作为当前有效通过；新证据不会覆盖旧事实；保存 Evidence 不造成无限自我失效。

### T-07｜实现结果审阅与人工接受

**阶段：M1。依赖：T-06、T-11、T-12。关联：D-08、D-16、D-24。**

目标：用户不用翻遍 Chat 就能判断是否接受。

交付：准出清单、diff/文件入口、材料预览、来源/版本展示、继续修改/接受/放弃动作。验收：必选条件不足时不能伪装完成；有权限的人才能接受；Agent 不能自行放弃或接受。

### T-08｜实现 Workspace Merge Queue 与最终复验

**阶段：M1。依赖：T-03、T-06、T-07。关联：D-05、D-06、D-13。**

目标：并发候选只通过受控串行路径改变 canonical state。

交付：队列、锁、最新基线检查、候选对齐、规定复验、批准适用规则与状态展示。验收：两个接受不交错污染；主干前移后不沿用旧证据；发生实质变更时重新审阅；完整合入前不误报 Accepted。

### T-09｜补齐多仓库部分成功与外部写入处理

**阶段：M1 的必要防护；高级恢复可后续增强。依赖：T-08。关联：D-01、D-05、D-06。**

目标：不把串行锁误当原子事务。

交付：集成记录、部分成功检测、暂停队列与明确恢复入口；canonical 外部改动检测。验收：在仓库 A 完成后模拟 B 失败，不显示全部成功、不继续后续 merge、不粗暴覆盖外部修改。

### T-10｜统一 Blocked / Resume 与中断恢复

**阶段：M1。依赖：T-01、T-03；与 T-04～T-09 并行完善。关联：D-02、D-07、D-08。**

目标：机器、工具故障的自动恢复与需要人回应的 Blocked 都保留同一 Issue；只把确需人介入的情况表达为 Blocked。

交付：自动恢复/等待的进度与原因、人工请求的责任方/下一步、内部重试边界、继续执行入口及必要恢复记录。验收：掉线、工具错误或 handoff 后不要求用户创建 Run；系统可自行处理时不请求人介入；重复回应或恢复不会盲目重复已完成的外部动作。

### T-11｜建立基础信任与接受权限

**阶段：M1；完整角色体系后置。依赖：T-01。关联：D-08、D-16、D-24。**

目标：远程控制与人工接受有实际权限边界。

交付：Daemon 鉴权、Workspace 路径范围、工具/资源授权、敏感凭证隔离、接受身份及记录。验收：未授权客户端、Agent 输出或普通聊天参与者不能自行改变 canonical state；清晰声明可信单用户及插件假设。

### T-12｜证据持久化、预览与保留

**阶段：M1。依赖：T-03、T-04；支持 T-06、T-07。关联：D-10～D-13。**

目标：材料可读、可访问且不随清理消失。

交付：最小存储方式、引用、访问控制、文件大小边界、主动内容隔离、必要脱敏及清理规则。验收：清理 worktree 后接受记录仍能打开证据；权限一致；证据缺失有明确状态，不保持虚假的绿色。

### T-13｜端到端测试与开源准备

**阶段：M1。依赖：首发范围内上述任务。关联：D-25 及 M1 清单。**

目标：让外部用户能复现产品价值与限制。

交付：第 24 节选定场景的测试记录、安装说明、支持矩阵、样例 Workspace、故障恢复说明、许可证与依赖/品牌/认证核对。验收：干净环境可完成一次完整闭环；文档不宣传尚未提供的安全和原子性保证。

### T-14｜Simulator 与单机资源竞争试点

**阶段：M2。依赖：M1、最小资源契约。关联：D-20。**

目标：用用户正在做的 iOS App 验证共享资源调度需求，聚焦多个 Issue 对已接入 Simulator 的竞争与复用。

交付：受支持环境清单、Simulator 分配/独占/排队/释放/重置、健康检查与故障回收，并用实际验证材料检查环境归属。Simulator 操作、截图录屏与测试采集属于基础 Tool Use，按移动端验证场景先接入，不等待本调度试点。验收：两个 Issue 争用同一实例时有明确等待，不互相接管；清理失败的实例不会继续当作健康资源发放。

### T-15｜跨 Host 验证试点

**阶段：M3。依赖：T-14 或其他已稳定资源 Provider。关联：D-20、D-21。**

目标：用一个真实任务证明构建与验证可以分离。

交付：多 Daemon 资源登记、传输/部署、环境与构建身份绑定、断线恢复。验收：使用旧构建或错误环境时不能冒充当前成功；网络中断不会造成重复持有或未经授权的动作。

### T-16｜IM、团队与云端的后续设计包

范围补充：当前 README 将 IM 接入、账号与权限体系、云端 Workspace 分别列项。IM 的消息与任务交互独立于团队管理；账号绑定和统一授权是两者需要对齐的依赖契约。云端 Workspace 托管文件与持久状态，不要求执行托管。

**阶段：M4～M6。依赖：稳定的 Issue、权限、资源和执行边界。关联：D-22～D-24。**

目标：分别形成通用 Bot Adapter 契约与 Lark MVP 方案、账号和团队权限方案，以及云端 Workspace 文件访问、版本和恢复的可行性验证。

交付与验收按独立 Issue 拆分，不合成一个“完成所有平台化”的大任务。每个扩展都必须复用同一 Issue / Evidence / Acceptance 语义，不复制业务状态。

## 24. 跨模块验收场景与指标

### 24.1 必须用失败路径验证闭环

| 编号   | 场景                               | 预期结果                                                                            |
| ------ | ---------------------------------- | ----------------------------------------------------------------------------------- |
| E2E-01 | API Bug 修复：包含合法与非法输入   | 原始请求响应和检查结果可审阅，接受后合入正确候选                                    |
| E2E-02 | Web UI 修改：浏览器操作和截图      | 证据来自本 Issue 的正确页面/构建，不依赖父页面跨域 DOM                              |
| E2E-03 | 两个 Issue 并发修改同一 Workspace  | 候选隔离，最终集成串行，后合入者对齐最新状态并复验                                  |
| E2E-04 | 证据生成后继续改代码               | 原判断保留历史但不再算当前有效通过                                                  |
| E2E-05 | 用户审阅后主干前移                 | 不能把旧截图和旧测试直接当作新候选的准出依据                                        |
| E2E-06 | Daemon 中途离线后恢复              | 同一 Issue 可自动恢复，恢复进度可见；只有需人处置时才进入 Blocked，用户不管理新 Run |
| E2E-07 | Agent 请求业务澄清                 | 用户收到具体问题，回答后继续同一 Issue                                              |
| E2E-08 | 工具退出失败或验证无结论           | 真实失败/不确定可见，不以“有报告文件”代替通过                                       |
| E2E-09 | 多仓库 A 合入成功、B 失败          | 显式部分完成，队列暂停，恢复不覆盖未知外部写入                                      |
| E2E-10 | 无权限用户从 Web/IM 尝试接受       | 被拒绝且不改变 canonical Workspace                                                  |
| E2E-11 | 用户放弃未完成 Issue               | 不自动合入候选；资源清理与证据保留遵守策略                                          |
| E2E-12 | 清理 worktree 后重新查看已接受结果 | 所需证据仍可读取，候选与最终结果可追溯                                              |
| E2E-13 | 两个 Issue 争用一个 Simulator      | 申请、等待、释放有序，环境状态不串扰                                                |
| E2E-14 | 跨 Host 使用了过期构建             | 版本不匹配被识别，结果不能算作当前验证通过                                          |
| E2E-15 | 教师备课/PPT 或数据处理交付        | 原文件与适当检查材料可审阅，不强迫其伪装成代码测试                                  |
| E2E-16 | Candidate 修改了测试/准出脚本      | 变更可见，不能由候选自改规则后自行授权通过                                          |

前十二项构成首发范围的主要候选；浏览器等条件项随首发承诺选择，Simulator、多 Host 与非代码完整模板按阶段加入。

### 24.2 建议观测的指标

| 指标               | 说明                                                                | 防止误读                                         |
| ------------------ | ------------------------------------------------------------------- | ------------------------------------------------ |
| 有效交付吞吐       | 单位观察周期成功接受并合入的 Issue 数                               | 不等于同时运行的 Agent 数                        |
| 人工介入负担       | 每个 Issue 的必要回答、纠错与恢复次数                               | 不把每条正常沟通都当缺陷                         |
| 审阅成本           | 用户理解候选、证据并作出决定的时间或操作量                          | 不以“更快点击接受”替代审阅质量                   |
| 证据有效性         | 缺失、过期、错版本或不足以支撑条件的占比                            | 不以“附件数量”衡量可信度                         |
| 等待与人工介入构成 | 区分自动等待/恢复与需人的 Blocked，记录资源、掉线、问题、权限等原因 | 不把系统等待一律标为 Blocked；按原因选择后续优化 |
| 集成稳定性         | 对齐失败、复验失败、部分合入与恢复结果                              | 不把错误藏在成功率分母之外                       |
| 资源效率           | 排队、持有、空占、清理失败                                          | 不能为提高利用率破坏隔离                         |
| 交付后返工         | 接受后因未满足条件而需要修复的情况                                  | 是检验证据和准出质量的反馈                       |

暂不设没有依据的硬指标目标。先记录自身工作流基线，再用同类任务比较。

### 25.3 主要风险

| 风险                     | 可能表现                                  | 当前应对                                |
| ------------------------ | ----------------------------------------- | --------------------------------------- |
| 退化为另一个 Chat 壳     | 用户仍自己管理验证、恢复和合并            | 以证据到接受的完整闭环作为 M1 验收      |
| 抽象过度                 | 先造 Run、Asset、插件市场和云文件系统     | 守住已确认最小领域模型                  |
| 错把 Evidence 当事实真理 | 工具输出真实，但测试不足或绑错版本        | 原始材料、判断、版本身份与覆盖范围分离  |
| 过期批准                 | rebase/冲突修改后沿用旧接受               | 明确批准适用范围与重审触发              |
| 多仓库部分完成           | 用户看到完成，但 Workspace 混合了新旧版本 | 记录集成过程，检测并停止，提供恢复路径  |
| worktree 安全幻觉        | 文件分开，但进程、端口、凭证仍共享        | 明确隔离层次，资源与权限补齐            |
| 资源调度过早做大         | 大量时间投入通用框架，真实场景仍跑不通    | 从端口 + 单一浏览器/Simulator 场景验证  |
| 凭证与插件信任扩大       | 执行侧可控制管理面或读取过多秘密          | 最小权限、控制/执行面边界、可信插件声明 |
| 竞品能力被低估           | 将已有通用功能误认为独有卖点              | 按官方能力更新，实测差异化组合          |
| 通用愿景稀释切入         | 同时承诺软件、文档、移动端与云            | 明确首发场景，保留模型通用性但缩小承诺  |

## 26. Issue 模板、术语修正与对话覆盖索引

### 26.1 可复制的 Issue 模板

这是面向人的 Markdown 工作模板，不是已冻结 API Schema。

```markdown
# Issue：<要实现的目标>

## 背景与意图

为什么需要这项工作？目前有什么问题？

## 目标

完成后，用户或 Workspace 应获得什么变化？

## 范围与非目标

允许修改哪些仓库/目录？这次明确不做什么？

## 约束

兼容性、环境、权限、预算、不可影响的行为等。

## 准出条件

- [ ] AC-1：<可观察的完成条件>
- [ ] AC-2：<可观察的完成条件>

## 验证与 Evidence 计划

| 条件 | 证明什么   | 材料形式                   | 采集方式 / 环境  | 判断方式             |
| ---- | ---------- | -------------------------- | ---------------- | -------------------- |
| AC-1 | <目标行为> | <测试报告/请求响应/截图等> | <实际工具和资源> | <断言/模型初审/人工> |
| AC-2 | <目标行为> | <材料>                     | <环境>           | <方式>               |

## 需要的资源与权限

<工具、Host、端口、Browser、Simulator、测试数据等>

## 执行中的问题

<需用户回答的问题；由系统呈现阻塞原因>

## 结果审阅

<候选变更摘要、材料链接、判断与未解决问题>

## 接受与集成记录

<由系统记录批准者、对应候选、最终验证与合入结果>
```

后两部分应由系统或受控流程产生，不要求用户手工维护 Git 版本或内部会话 ID。

### 26.2 建议的文档维护方式

先将本文作为产品决策基线，T-01～T-16 按现有项目工作方式拆成可执行 Issue。实现时可逐步形成专门的 Evidence、Merge Queue、Resource Provider 设计文档，但不要把同一个决策复制成多份互相冲突的说明。

当新信息导致变更，应记录：改变了哪项 D 编号、旧决定是什么、新决定是什么、为什么改变、哪些任务和验收受影响。已确认事项可以演进，但必须显式演进。

### 26.5 进入实施后的第一条主线

**先不扩大概念，先完成一次可信交付：** 人确认一个 Issue 的完成标准，Agent 在隔离候选中工作，真实工具产生绑定正确状态的证据，人能够直接审阅，系统在最新 canonical state 上复验并安全合入。

这条路径成立之后，再用 Simulator、跨 Host、IM、团队和云端扩展它。产品的复杂度可以增长，但用户应始终只需要理解：**我要做什么、现在为什么停住、证据说明了什么、是否接受。**
